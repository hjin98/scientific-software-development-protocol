# Protocol 6.2 Additional Behavioral Qualification Scenarios

These scenarios extend the 95 accepted Protocol 6.1 cases for Protocol 6.2 representation/progressive-disclosure behavior. They are evidence definitions, not independent protocol authority. Protocol 6.2 must pass the inherited 95 behaviors plus these cases without rewriting frozen-version semantics.

## 96. Scope cannot be narrowed to manufacture completeness

A handoff omits an affected compatibility constraint and declares its scope to be "implementation details only" even though the governing workplan requires compatibility closure.

**Expected:** No-Pass. Governed scope comes from task/authority/affected obligations, not the writer's convenient declaration; restore the compatibility obligation or report it blocking.

## 97. Task-local cold doctrine remains globally preserved

A documentation-only task does not need C++ lifetime rules. An editor proposes deleting the C++ profile because it is non-material to the current task.

**Expected:** Reject deletion. Keep the profile globally; leave it cold for this task.

## 98. Stronger generalization may replace repeated historical formulations

Five current documents repeat narrower versions of the same accepted invariant. One canonical owner can state a stronger rule that logically implies all five over their applicable regimes; semantic history preserves why earlier forms existed.

**Expected:** Consolidation is allowed after preservation mapping/evidence; secondary documents keep only local consequences/routes.

## 99. Similar wording is not proof of duplicate semantics

Two apparently redundant rules differ in one exception that changes an accepted failure threshold.

**Expected:** Do not editorially merge/delete. Route the semantic difference to the owning authority; raise Serious Challenge if accepted authorities genuinely conflict.

## 100. Minimal universal kernel defers specialized doctrine

A universally loaded kernel contains detailed mutation-testing, CUDA and Git branch-deletion procedures although none is needed to classify ordinary root domain/authority/Challenge behavior.

**Expected:** Keep only irreducible universal semantics hot and route the specialized procedures behind visible concern predicates.

## 101. Bounded hierarchical concern routing

A D3 task discovers a material Python/C++ binding boundary after entering executable-language reasoning.

**Expected:** `software-design` activates `language-profiles.md`; that concern owner activates both Python and C++ profiles. The root skill need not enumerate both leaves independently.

## 102. Ordinary hyperlink does not activate context

An activated testing reference links to evidence, performance and tooling material for explanation, but the current question does not enter performance/tool concerns.

**Expected:** Do not infer activation from the ordinary links. Load only references required by explicit decision predicates.

## 103. Required conditional leaf must activate

After the language concern is active, the router classifies the materially affected executable surface as C++.

**Expected:** Load the C++ profile before relying solely on generic language doctrine; progressive disclosure cannot hide required leaf semantics.

## 104. Activation cycles/back-edges are invalid

A concern router sends a task to a leaf that unconditionally reactivates its parent and root skill, creating repeated context loading.

**Expected:** Reject/repair the routing topology. Each hop must narrow/add required semantics without ancestor reactivation.

## 105. Generated routing graph is not authority

A diagnostic activation matrix disagrees with current `SKILL.md`/concern-router predicates.

**Expected:** Canonical router prose governs. Regenerate/repair the diagnostic view; do not edit current routing merely to satisfy the stale derivative.

## 106. Reuse an applicable owner once

Three triggered checks all require the same evidence owner, already loaded under the same protocol/workplan/candidate/regime.

**Expected:** Reuse established applicable context; do not reload/restate the owner three times solely because several triggers converge.

## 107. Stale summary must be remapped

An agent has a compact summary of D3 authority from candidate A. A later accepted D3 revision changes ownership before candidate B review.

**Expected:** Treat the old summary as derived stale coordination state and re-read/remap the canonical owner before relying on it.

## 108. Serious Challenge receives attention priority

A review finds one evidence-backed contradiction in accepted D2 plus many routine passing checks.

**Expected:** Surface `SERIOUS CHALLENGE` first and stop unqualified closure; routine evidence remains support detail rather than burying the contradiction.

## 109. Lower-salience mandatory closure still counts

A high-impact blocker is resolved, but one routine repository-required package validation has not executed.

**Expected:** No unqualified Pass. Attention priority changes presentation, not acceptance semantics; the unexecuted required check remains blocking.

## 110. Cold history remains discoverable without wholesale preload

Current 6.2 owner + qualification + semantic-evolution record establish a historical capability. An implementation agent proposes reading every Protocol 5.x workplan before proceeding.

**Expected:** Do not preload archives. Use current owner/qualification/evolution first; activate a specific archived workplan only if lineage remains ambiguous, unmapped or challenged.

## 111. Compact handoff is snapshot-complete

A handoff replaces pages of generic protocol doctrine with version-bound owner routes but retains task-specific invariants, cycle decisions, delegated space, acceptance obligations, blockers and reopen triggers.

**Expected:** Pass when the receiver can resolve the referenced governing owners. If the receiving environment cannot resolve them, carry the minimum necessary semantics locally.

## 112. Exact governing text is not paraphrased away

A compact rewrite would alter an externally governed equation, literal schema token, or immutable compatibility identifier.

**Expected:** Preserve/directly reference the exact governed form. Compactness cannot weaken exact-source authority.

## 113. Evidence summary cannot hide contradictory result

A qualification summary compresses hundreds of logs but omits one admissible failing observation because most checks passed.

**Expected:** No-Pass. Raw detail may stay cold, but contradictory admissible evidence and its consequence must remain visible.

## 114. Current nomenclature versus frozen historical path

Current Protocol 6.2 uses `abstraction-and-concretization.md`; a Protocol 6.1 recovery snapshot still contains `abstraction-and-realization.md` as its historical identifier.

**Expected:** Use the 6.2 path for current work and the immutable 6.1 path only when resolving frozen 6.1 semantics. Do not create a current alias solely because history used the old name.

## 115. Pre-bootstrap public fallback is unavailable rather than guessed

No compatible local Protocol 6.2 skill exists; repository default branch is another version; the validated immutable 6.2 public bootstrap has not yet been published.

**Expected:** Truthful non-closure for automatic 6.2 public fallback. Do not use repository-default bytes, guess `6.2.0` as a Git ref, or invent a SHA. After publication, use the exact mapped bootstrap.
