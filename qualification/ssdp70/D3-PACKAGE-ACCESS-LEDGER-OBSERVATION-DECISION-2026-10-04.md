## Gap (classified: D3, not D4)

Native `read` events and observer-captured tool-result text do not bound which package files an arbitrary subject process (`bash`, and native `grep`/`glob`) read. In a run of the real OMP runtime driven by a scripted local stand-in provider, the subject obtained the T7 owner via `bash cat`; the harness reported no owner read and root-only bytes yet `COMPLETE_ADMISSIBLE` (`OMP-STANDIN-20261004T171724Z-…/run`). The D4 guard that now makes such runs `INADMISSIBLE` (`OMP-STANDIN-20261004T172146Z-…/run`) prevents a false claim but cannot supply the exact observation the burden metric needs. The accepted graph does not say which principal observes subject-process package access, so a D4 choice would silently decide an architecture question.

## Decision

1. **Owner.** The *qualification supervisor principal* observes access to the installed protocol package. The package tree is already a supervisor-owned immutable input that the subject receives read-only (`/opt/ssdp/skills`). Observation is a supervisor evidence-capture duty ("run identity/evidence capture").
2. **Mechanism class (D4 may substitute an equivalent).** A kernel-maintained per-inode access record taken on the supervisor's own host-side package directories (Linux inotify marks on the installed tree: open, access, close, mutation, overflow, unmount). It records accesses by *any* process that reaches those inodes through any path or mount, with no cooperation from, or channel to, the subject.
3. **Topology.** No new principal, process, socket, proxy, credential carrier or cross-principal communication edge. The subject gains no capability; the supervisor receives information only from the kernel about its own files. The subject cannot read, write or influence the ledger; a failure to observe is itself recorded. Unchanged: provider-control observer scope, mediator ownership, MCP bridge, subject authority.
4. **Ledger = upper bound; supply = content that identifies the opened file.** The ledger bounds *which package regular files were opened*. A file counts as *consumed* only when model-visible tool-result text (hash-linked request bodies, via the existing observer chain) supplies content **that identifies that file**: (a) native `read` through the existing `consumption` rule; or (b) for process output, a contiguous match (the whole file, or a run of at least the distinctiveness floor) that is **either** distinctive — contained in no other file of the installed package — **or** produced by an action whose own recorded input names the file's package path. Byte-identical twins, content shared between files (for example an inlined kernel block) and sources shorter than the floor are therefore never explained by content alone; an open of such a file is explained only by path linkage. Content shown for a different file, however similar, never explains an open. Supply does not require ordering relative to the open: attribution rests on identity, not time. An opened file with no such supply is **unexplained**. Unexplained access, ledger loss (overflow, lost mark, unmount, mutation, mark not established, read error, row-bound exceeded, missing artifact) or an observed-content/ledger contradiction makes resource observation **not exact**, and a not-exact observation makes T1/T7/T8 burden claims `INADMISSIBLE` (never a lower-bound PASS). Files never opened are *exactly* not consumed: a run whose root was delivered at request 0 with no further package access is an **exact entrypoint-only observation** (bytes = the delivered root `SKILL.md`), and a post-request re-open of a root whose full content was delivered is explained by delivery.
4a. **Exactness is per question.** The byte question (burden) needs every opened file explained. The **owner-read question** (was any owner copy read, when) needs the ledger intact and every opened owner copy explained, whatever happened to unrelated files. A summary carries both (`exact`, `owner_read_exact`); `active_ssdp_bytes` is null unless `exact`, `owner_read_sequences` is null unless `owner_read_exact`. Campaign-level owner false-activation is unresolved only when some run's owner question is not exact; unrelated unexplained opens elsewhere do not void it. Burden/T7-mode claims need `exact`; owner claims need `owner_read_exact`. **Owner-read time** is defined in item 6.
5. **Phase split by request 0.** Opens before the hash-linked request-0 record are runtime-initiated (the model cannot act before it has a response). They are explained only when they are `<root>/SKILL.md` entries (catalog/activation); any other pre-request open is unexplained. Model-driven reads cannot precede the response, so opens at or after request 0 must be explained by supply or delivery. **Supply matching is independent of phase**: the phase decides only which opens are classified unexplained. Ledger stamps are wall-clock (`CLOCK_REALTIME`) drain times, no earlier than the event; the cut is the observer's request-0 record stamp, taken after the full request body is read and before it is forwarded, and request 0 is the first allowed POST (the transform declares no auxiliary POSTs). Consequently clock skew can change only (i) a non-entrypoint open into the stricter pre-request class, or (ii) the exactness label of an unshown root `SKILL.md` open; it cannot change counted bytes or owner sequences. A wall-clock step is not excluded; it is bounded to those two effects.
6. **Counting.** Active SSDP bytes remain the contract metric: the root `SKILL.md` delivered/read plus each package file whose content reached the model (item 4), each counted once at full installed size; a byte-identical twin counts only when it was itself supplied. Native `read` behavior is unchanged. **Owner-read time (the owner-read sequence set).** An owner read is *access*, not only display: the earliest sequence at which an owner copy was read is the earlier of (a) the events that supplied it and (b) the **access bound** of its first ledger open. The access bound maps the first open stamp to the first retained provider request stamped after it (the open belongs to the turn whose results that request first carries) and takes the smallest sequence among the tool-result events first delivered in that request; an open after the last request has no later model-visible event and is bounded by the end of the trace. Same-turn ties resolve to the earliest event (conservative for the zero-tolerance floor; an R2 event in the same turn is ambiguous R2 timing under the contract). If an owner copy was opened at or after request 0 and the mapping cannot be resolved, the owner question is not exact. Without (b), `wc -l owner` before R2 followed by a later full display would score as a read after R2. The mapping uses the same clock-skew bound as item 5 (a late drain stamp can only move the bound later by one turn, never change counted bytes). Owner copies are every package file whose basename is the owner's.
7. **Adapter scope.** The ledger is an adapter-produced supervisor artifact bound into the evidence-integrity chain. Its rows fold repeated events per (file, flags) with first/last stamp and count and are bounded, so subject access volume cannot grow the record; the bound being exceeded is ledger loss. An adapter that produces no ledger keeps the previous behavior: process execution makes burden/owner claims `INADMISSIBLE`.

8. **Rehearsal gate (required before any adapter/profile using this ledger is admitted for a burden or owner claim).** The independent pre-run checker runs, through the exact adapter/profile and the shipped package shape (twin groups included), an executor rehearsal covering at least: native `read` of a skill URL and path; `bash cat` with an absolute path; `cd <root> && cat references/x`; glob and brace paths; shell variable and loop forms; `grep -r`, native `grep`/`glob` over the package; `wc`/`grep -c`/`head`; a command mixing a successful read with a failing command; a multi-turn run with compaction or other runtime rescan of the package. It reports, per form, `exact` and `owner_read_exact` and the cause. The acceptance threshold is derived by the stakeholder or contract owner from the campaign's run count N and the aggregation rule that **any run with `owner_read_exact` not true makes owner false activation UNRESOLVED for the whole campaign**; a per-run rate p supports a campaign only if (1−p)^N is acceptable. Until a threshold is accepted the gate is unmet and no such claim is admitted. Whether a replacement run may restore an inexact original is a contract question (replacements never remove originals); this decision does not decide it.

## Considered and rejected

- Remove `bash`/native process tools: contradicts the preserved 6.6 allow classes for T1/T7/T8.
- Observation via a FUSE or proxy filesystem serving the package: a new service and cross-principal edge; reopens D3.
- Content-matching alone: cannot prove absence of reads (a model can transform output); retained only as supply evidence.
- Conservative claim-scoped inadmissibility only: remains the fail-closed fallback, but forfeits a feasible exact observation inside the accepted graph.

## Residuals and non-claims

- Execution of arbitrary subject processes remains unauditable by pid; attribution is by identity of the supplied content or by the action's recorded path, not process identity.
- A read whose output is transformed (hash, base64, count) or scanned without being shown (`grep -c`, `grep -l`, `wc`, `grep -r … | head`, native `grep` over the package) is *unexplained*, so the byte question is not exact and the burden claim is conservatively inadmissible; this is intended. Only the owner question is isolated from it (item 4a).
- Tool results with error status are not supply even when the model saw the content (stricter, conservative). A stray non-zero exit (`cat a; cat missing`) therefore makes the shown file unexplained.
- **Shipped package shape.** The generated package at the time of this revision has 238 files with 63 distinct contents; 213 files are in 38 byte-identical twin groups, including the owner (seven copies) and every reference file. Distinctive content therefore identifies almost nothing; for process-read references attribution rests on a literal package path in the action input. Honest non-literal forms (`cd <root> && cat references/x`, globs, brace expansion, shell variables, `find -exec`/`xargs`/loops) are *unexplained*, making the run inexact. This is fail-closed, not unsound.
- Path linkage tests that the input names the file, not that the action opened it. An action that names a twin while showing the other twin's identical content explains an unshown open of the named twin and counts it; the effect over-counts bytes and can add an apparent second owner read. It never under-counts.
- The distinctiveness floor in item 4 is a D4-delegated minimum block size (48 bytes at this revision), not a D3 constant.
- Whether other adapters/runtimes can realize an equivalent observation is unresolved; no claim is made for them. Package root layout `/opt/ssdp/skills/<root>/...` is assumed only for this OMP profile.
- The mechanism depends on host kernel inotify semantics; exactness is claimed only for ledgers that report established, complete, non-overflowed marks. The three inotify sysctl limits are host conditions to be recorded with the host execution identity.
- **Open for owner acceptance (not decided here):** (i) workplan "Root-selection evidence contract" says burden claims are inadmissible "if the exact OMP build cannot expose that consumption"; this decision reads supervisor kernel observation plus observer-seen supply as an admissible exposure. On acceptance that bullet needs an `[Affected by …]` annotation (proposed, pending independent check: a marker at that bullet and contract revision 9 §1 item 13, `PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md`). (ii) Contract §1 item 4 scores owner reads "from complete `resource_access` records"; ledger-derived consumption is a supervisor accounting record in the summary, not a normalized event. Acceptance must either route a contract amendment (normalized derived event, schema version, completeness accounting) or explicitly accept the accounting record as the owner-read source for this profile. Proposed resolution, pending independent check and stakeholder decision: the contract amendment route (contract revision 9, §1 item 13 `package_access` event). (iii) The rehearsal gate is an **acceptance boundary** (item 8), not an open remark.

## Reopen triggers

Reopen D3 if realization needs any new principal/channel/edge, if distinctive-content-or-path attribution cannot identify an opened file on a package shape the project ships, if the subject gains the ability to influence or suppress marks, or if the contract metric changes from consumed-bytes to something the ledger plus supply cannot decide, or if the item 8 rehearsal gate fails (honest executor behaviour makes the byte or owner question inexact at a rate the campaign aggregation cannot absorb). Pre-registered fallback to evaluate on reopen: attribution of an open to the turn window (request-interval) in which its content was shown, which handles non-literal paths at the cost of clock dependence already accepted for owner-read time in item 6; the alternative is claim-scoped inadmissibility.

## D4 acceptance boundary

Real OMP → trusted observer → harness/core → scorer path: (a) `bash cat` owner yields exact bytes and an owner-read sequence; (b) accesses whose content cannot be shown supplied (count/hash/grep/transform/`wc -c`) yield `INADMISSIBLE` for burden claims with the file named, **including when other package files with overlapping or byte-identical content were shown** (shared kernel block; twin owner copy); (c) non-read mutation, ledger overflow, missing ledger and ledger/native contradiction are rejected; (d) pre-request opens other than `SKILL.md` are rejected; (e) previous guard behavior for ledger-less adapters is preserved; (f) retained failed and earlier realizations stay append-only; (g) an entrypoint-only run (no tool call, listing only, or a size probe of the delivered root) with an exact ledger is `COMPLETE_ADMISSIBLE` for burden claims; (h) an unrelated unexplained open leaves the owner-read question exact and the owner-read sequences observed; (i) a ledger-less adapter keeps the process-execution guard; (j) an owner open before R2 whose content is shown only after R2 yields an owner-read sequence at or before the R2 event, while an unrelated open of a non-owner file does not; (k) the burden claim gate rejects a deterministic root selection whose delivery proof failed even when the ledger is exact; (l) owner copies are recognized by one rule (basename) in accounting and in the harness.

## D4 realization facts observed (development evidence, not admission)

- Before request 0 the runtime opens exactly the seven roots' `SKILL.md` files (catalog scan) and nothing else in the package; the pre-request rule therefore needs no exception beyond `<root>/SKILL.md`. This is an observation of this build, not a contract constant; any other pre-request open is classified unexplained.
- Original counterexample re-realized (`bash cat` of the T7 owner): `COMPLETE_ADMISSIBLE`, resource observation exact, active bytes 14 454 (root) + 45 958 (owner) = 60 412, owner-read sequence recorded. The earlier false state (root-only 14 454, no owner read) is retired by observation, not by guard.
- Content that cannot be shown supplied (`wc -l`, `base64 | head`, native `grep` over the package) yields `INADMISSIBLE` for burden/owner claims, names the opened files, and leaves `active_ssdp_bytes`/`owner_read_sequences` null.
- The kernel mechanism distinguishes `open`+`access` (read) from `open` only (`wc -c`); the accounting treats both as access that must be explained.
- `package_ledger.py` is supervisor code bound into the execution-profile identity with the adapter, core and harness digests.
