## Gap (classified: D3, not D4)

Native `read` events and observer-captured tool-result text do not bound which package files an arbitrary subject process (`bash`, and native `grep`/`glob`) read. In a run of the real OMP runtime driven by a scripted local stand-in provider, the subject obtained the T7 owner via `bash cat`; the harness reported no owner read and root-only bytes yet `COMPLETE_ADMISSIBLE` (`OMP-STANDIN-20261004T171724Z-…/run`). The D4 guard that now makes such runs `INADMISSIBLE` (`OMP-STANDIN-20261004T172146Z-…/run`) prevents a false claim but cannot supply the exact observation the burden metric needs. The accepted graph does not say which principal observes subject-process package access, so a D4 choice would silently decide an architecture question.

## Decision

1. **Owner.** The *qualification supervisor principal* observes access to the installed protocol package. The package tree is already a supervisor-owned immutable input that the subject receives read-only (`/opt/ssdp/skills`). Observation is a supervisor evidence-capture duty ("run identity/evidence capture").
2. **Mechanism class (D4 may substitute an equivalent).** A kernel-maintained per-inode access record taken on the supervisor's own host-side package directories (Linux inotify marks on the installed tree: open, access, close, mutation, overflow, unmount). It records accesses by *any* process that reaches those inodes through any path or mount, with no cooperation from, or channel to, the subject. Directory marks report by parent dentry; they are equivalent to per-inode marks here only because the installed tree is one fresh copy exposed through one read-only bind with no hard links. That equivalence is a premise of this profile (a package with hard links or several binds reopens D3).
3. **Topology.** No new principal, process, socket, proxy, credential carrier or cross-principal communication edge. The subject gains no capability; the supervisor receives information only from the kernel about its own files. The subject cannot read, write or influence the ledger; a failure to observe is itself recorded. The supervisor heartbeat source of item 5 lives outside every path the subject can reach and adds no edge. Unchanged: provider-control observer scope, mediator ownership, MCP bridge, subject authority.
4. **Ledger = upper bound; supply = content that identifies the opened file.** The ledger bounds *which package regular files were opened*. A file counts as *consumed* only when model-visible tool-result text (hash-linked request bodies, via the existing observer chain) supplies content **that identifies that file**: (a) native `read` through the existing `consumption` rule; or (b) for process output, content that is **one** of: (i) a contiguous match (the whole file, or a run of at least the distinctiveness floor) that is *distinctive*, contained in no other file of the installed package; (ii) a contiguous match produced by an action whose own recorded input names the file's package path; or (iii) the file's **whole** content (at least the floor size), contained in a tool result delivered within the open's candidate window (item 5). Route (iii) is what makes a byte-identical twin read through a non-literal path (`cd <root> && cat references/x`, a glob, a variable) explained: the model then holds that file's entire content. A shared block or a partial run of a non-distinctive file never explains an open by route (iii); sources shorter than the floor are explained only by (a) or (ii); content shown for a different, non-identical file never explains an open. Routes (i) and (ii) do not depend on ordering; route (iii) depends only on the mechanical bracket of item 5. An opened file with no such supply is **unexplained**. Unexplained access, ledger loss (overflow, lost mark, unmount, mutation, mark not established, read error, row-bound exceeded, missing artifact) or an observed-content/ledger contradiction makes the **byte** observation not exact, and a not-exact byte observation makes T1/T7/T8 burden claims `INADMISSIBLE` (never a lower-bound PASS). Files never opened are *exactly* not consumed: a run whose root was delivered at request 0 with no further package access is an **exact entrypoint-only observation** (bytes = the delivered root `SKILL.md`), and a post-request re-open of a root whose full content was delivered is explained by delivery.
4a. **Two questions, two exactness values; positive evidence is content that reached the model.** (A) The **byte question** (burden) needs every opened file explained (`exact`); `active_ssdp_bytes` is null unless `exact`. (B) The **owner floor** (zero-tolerance owner false activation: an owner read before the first predeclared R2 event; and the owner-load hits after R2) is judged as follows, whatever happened to unrelated files. *Positive evidence* of an owner read is **content that reached the model**: a native `resource_access` event with consumption, or **owner-class supply**, a tool result seen by the model that contains a contiguous run of whole owner lines of at least the floor length (the owner's whole content, or a partial read through any path form, relative or not). Each owner copy is byte-identical to the others, so owner content identifies the owner *class*, not a copy; owner-class supply is placed at **its own result sequence**, which the trace gives exactly, so it needs no timing and no path test. A positive owner read placed before the first predeclared R2 event is a **definite zero-tolerance FAIL** whatever the byte exactness, ledger loss or timing loss; a positive owner read placed after R2 and before the consequential step is an **owner-load hit**, which needs only that demonstrated supply and no exactness of any other file. *Negative conclusion* ("no owner read before R2") needs `owner_floor_exact` (the ledger established and intact, and timing intact, item 5) **and** that no owner copy was opened at a point that is not provably after R2: an owner open is **provably post-R2** only if the first trace event of its candidate window (item 5) follows the R2 event. An owner open that is not provably post-R2 and has no positive evidence (a package-wide `grep -r`/native `grep`/`find` scan, a `wc` or hash that shows no content, a transformed read, a runtime rescan, a scan before a legitimate post-R2 load) leaves the floor **UNRESOLVED and replaceable**: absence of an owner read cannot be concluded, and it is not a failure. Timing therefore only decides UNRESOLVED versus PASS-eligible, never a FAIL, and any imprecision errs toward UNRESOLVED. The summary publishes `exact`, `owner_floor_exact`, `owner_read_observed` (the positive evidence with its result sequences) and `owner_open_windows` (every opened owner copy with its candidate window). Campaign-level owner false activation is unresolved only for runs in the UNRESOLVED state. Burden claims need `exact`; an owner no-read conclusion needs `owner_floor_exact` and no owner open that is not provably post-R2.
5. **Phase split by request 0, a mechanical event-time bracket and candidate windows.** Opens before the hash-linked request-0 record are runtime-initiated (the model cannot act before it has a response). They are explained only when they are `<root>/SKILL.md` entries (catalog/activation); any other pre-request open is unexplained. Model-driven reads cannot precede the response, so opens at or after request 0 must be explained by supply or delivery. The cut is the observer's request-0 record stamp, taken after the full request body is read and before it is forwarded; **request 0 is the first subject-conversation request**, and auxiliary requests classified by the contract's frozen properties (contract §1 item 12) are not request 0 and do not delimit turns. **Ledger stamps are drain times, never earlier than the event, and draining can lag arbitrarily under supervisor contention; a drain stamp is therefore not an event time, and no lag bound is assumed.** The ledger carries a **mechanical ordering** instead: a supervisor-owned heartbeat source, outside every path the subject can reach, in the same kernel queue (one inotify instance keeps events from several watched directories in kernel order), with unique heartbeat names, so that each package event lies between two consecutive heartbeats. The event's real time then lies in a **bracket** whose lower edge is a stamp taken before the earlier heartbeat's write and whose upper edge is a stamp taken after the later heartbeat's write; scheduler or GIL lag can only widen a bracket, never make it wrong. D4 may use an equivalent mechanical ordering; an assumed lag bound is not equivalent. Heartbeats record `CLOCK_REALTIME` and `CLOCK_MONOTONIC`. **Timing loss** is a heartbeat gap, a bracket wider than a declared bound, or a divergence of the realtime-minus-monotonic offset from a **fixed per-run baseline** (taken at the first heartbeat) beyond a declared tolerance, and it taints every bracket from the first divergent heartbeat onward, not only an adjacent pair; timing loss makes `owner_floor_exact` false (positive evidence is unaffected, because it is placed by trace sequence). The observer stamps requests with `CLOCK_REALTIME`, so every bracket edge is widened by the declared clock tolerance before use. An open's **candidate window** is the span of trace events from the first event after the last subject-conversation request stamped before the bracket's lower edge to the last event before the first request stamped after its upper edge (the end of the trace if there is none). A retried request shares the original's conversation position; a window with no earlier request, an empty window or a pre-request open is treated as starting at the beginning of the trace, which is the conservative case. In-flight or background opens, opens after the last request and timing-loss opens (window from the beginning of the trace to its end) all receive a window containing the true time. "Event time" is the kernel's event generation; a lag between the syscall and event generation can only lower the lower edge, which widens the window. An open is *pre-request* if its lower edge precedes the cut and *post-request* if its upper edge is at or after the cut (a straddling open is both). Counted bytes depend on supply (items 4 and 6), not on phase; timing affects only phase classification, route (iii) and the provably-post-R2 test of item 4a.
6. **Counting; owner-class supply; parameters.** Active SSDP bytes remain the contract metric: the root `SKILL.md` delivered/read plus each package file whose content reached the model (item 4), each counted once at full installed size; a byte-identical twin counts only when it was itself supplied or explained by route (iii). Native `read` behavior is unchanged. Explanation for the byte question is **per file**: a file is explained if its content was supplied at any point (content already supplied cannot be supplied again, so no consumption is lost); route (iii) for an open whose window spans several turns accepts any of them, which is lenient only where the whole file reached the model anyway. **Owner-class supply** (item 4a) identifies owner content among tool results by whole owner lines at least the floor long; it rests on the premise, stated at whole-line granularity, that no non-owner file contains a whole owner line of at least the floor length (verified for the shipped package: 0 of 242 owner lines of 48 bytes or more occur in any non-owner file; at sub-line granularity 27 shared runs of 48 to 117 bytes do occur, so the premise is not claimed there; a package where a whole owner line is shared reopens D3). Owner copies are every package file whose basename is the owner's, and the owner corpus is the union of their lines. The parameters that decide results (the distinctiveness and owner-line floor, clock tolerance, bracket-width bound, heartbeat period and gap bound, row bound and the mark-lifetime bounds) are frozen in the execution profile before runs and recorded in the derived record; they are D4-delegated values, not D3 constants.
7. **Adapter scope.** The ledger is an adapter-produced supervisor artifact bound into the evidence-integrity chain. Its rows fold repeated events per (file, flags, heartbeat interval) with first/last bracket and count and are bounded, so subject access volume cannot grow the record beyond files times intervals; the bound being exceeded is ledger loss. The fold is a declared **reduction that is lossless for these oracles**: phase, the candidate window of each owner open (item 4a), and byte accounting need only the opens' brackets per interval, not the raw kernel stream. **Premises:** the supervisor opens no package file while marks are live and the marks outlive sandbox teardown (inotify records no pid, so a supervisor or observer open is indistinguishable from a subject open and would be unexplained or, if the owner, not provably post-R2). An adapter that produces no ledger keeps the previous behavior: process execution makes burden/owner claims `INADMISSIBLE`.

8. **Rehearsal gate (required before any adapter/profile using this ledger is admitted for a burden or owner claim).** The independent pre-run checker runs an executor rehearsal through the exact adapter/profile **for each arm's package shape** (the 7.0 candidate and the 6.6 and 6.5 comparators; the shape at this revision is 238/63/38/213, 212/62/37/187 and 198/60/35/173 for files/distinct/twin groups/twinned files), covering at least: native `read` of a skill URL and path; `bash cat` with an absolute path; `cd <root> && cat references/x`; glob, brace, variable and loop paths; `head`/partial reads through literal and non-literal paths (owner and non-owner); `PROTOCOL_VERSION` reads through non-literal paths (below the floor, so explained only by the native route or path linkage); `grep -r`, native `grep`/`glob`/`find` over the package; a package scan followed by a legitimate owner load after R2; `wc`/`grep -c`; a command that merely names an owner path (`ls`, `echo`, a grep pattern) without opening it; a command mixing a successful read with a failing command; request retries; a multi-turn run with compaction or other runtime rescan of the package (a rescan that opens owner copies leaves the owner floor UNRESOLVED); and a **timing-stress form** with supervisor CPU contention. It reports, per form, per arm and for each of the two questions of item 4a, the exactness, the cause and the **verdict** (definite FAIL, owner-load hit, PASS-eligible, UNRESOLVED, none), so that honest scans are seen as an UNRESOLVED rate, and the bracket-width distribution. Because demonstrating a very small per-run rate statistically is infeasible (about 1,500 clean honest runs bound it at 0.2%), the gate is **structural plus reported**: the common honest forms must be exact by construction, and the remaining inexact forms and their reported rates are judged against the campaign target of the stakeholder decision `STAKEHOLDER-DECISION-2026-10-04-PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER.md` (probability at least 0.8 that no unresolved run leaves the floor or route non-PASS, with replacement allowed where available), which the independent checker instantiates for the owner floor **and for each burden route** (T7 with the contract's unknown-value rule and pair addition) from the frozen run count N, the aggregation rules (any run UNRESOLVED on the owner floor leaves that floor unresolved unless replaced; any inexact burden run is an unknown value in its route) and the replacement rule. Until the target is instantiated the gate is unmet and no such claim is admitted. Replacement and T7 semantics are owned by contract §1 item 13, not by this decision.

## Considered and rejected

- Remove `bash`/native process tools: contradicts the preserved 6.6 allow classes for T1/T7/T8.
- Observation via a FUSE or proxy filesystem serving the package: a new service and cross-principal edge; reopens D3.
- Content-matching alone: cannot prove absence of reads (a model can transform output); retained only as supply evidence.
- Conservative claim-scoped inadmissibility only: remains the fail-closed fallback, but forfeits a feasible exact observation inside the accepted graph.

## Residuals and non-claims

- Execution of arbitrary subject processes remains unauditable by pid; attribution is by identity of the supplied content or by the action's recorded path, not process identity.
- A read whose output is transformed (hash, base64, count) or scanned without being shown (`grep -c`, `grep -l`, `wc`, `grep -r … | head`, native `grep` over the package) is *unexplained*, so the byte question is not exact and the burden claim is conservatively inadmissible; this is intended. The owner-access question is isolated from it (item 4a).
- Tool results with error status are not supply even when the model saw the content (stricter, conservative). A stray non-zero exit (`cat a; cat missing`) therefore makes the shown file unexplained.
- **Shipped package shape.** The generated package at the time of this revision has 238 files with 63 distinct contents; 213 files are in 38 byte-identical twin groups, including the owner (seven copies) and every reference file. Distinctive content therefore identifies almost nothing. For process-read references attribution rests on a literal package path (route (ii)) or on whole-file same-turn delivery (route (iii)); honest non-literal forms that show the whole file (`cd <root> && cat references/x`, globs, brace expansion, shell variables, loops) are explained by (iii). Partial reads of a twin through a non-literal path (`cd … && head -n 40 references/x`) and any unshown read remain *unexplained*, so the byte question (and owner-load) is inexact; the owner-access question is not affected. This is fail-closed, not unsound.
- Path linkage tests that the input names the file, not that the action opened it. An action that names a twin while showing the other twin's identical content, or (route (iii)) a same-turn open of a twin whose whole content was shown for the other twin, explains the unshown open and counts it. The model then holds that file's entire content, so the file is correctly counted as consumed, but the same bytes can be counted twice and add an apparent second owner read. Over-counting is conservative on the candidate arm against its bounds, but it also inflates the 6.5/6.6 comparator denominators of the 2.0x and median-plus-bounds comparisons; the direction depends on the arm. It never under-counts the candidate's consumption.
- An owner open that is not provably post-R2 and has no positive evidence (package-wide scans, a runtime rescan, `wc` or hashes that show nothing, transformed or hidden reads, a scan before a legitimate post-R2 load) leaves the owner floor UNRESOLVED and replaceable, never a FAIL. The cost is a **detection hole**: a model that systematically reads the owner by a form that shows no recognizable owner lines is repeatedly UNRESOLVED instead of FAIL, and an honest scan before a legitimate post-R2 load costs a replacement; the contract's replacement cap, the disclosure of every original and the per-arm inexact-rate bound limit what replacement can hide, and the multi-turn rehearsal measures the UNRESOLVED rate. A pre-R2 peek that shows nothing (`wc -l <owner path>`) is not a read of content and is UNRESOLVED, not a FAIL. In a real OMP run (stand-in provider, seven requests) a `grep -rl` over the package opened all 238 files including the seven owner copies with no owner content shown; compaction and long sessions are untested.
- A subject can fill the kernel queue by access volume (observed: 16,385 events with 9,000 opens while undrained), which is recorded as overflow loss. Overflow is therefore replaceable only with its cause disclosed and counted in the per-arm inexact-rate.
- The distinctiveness floor in item 4 is a D4-delegated minimum block size (48 bytes at this revision), not a D3 constant.
- Whether other adapters/runtimes can realize an equivalent observation is unresolved; no claim is made for them. Package root layout `/opt/ssdp/skills/<root>/...` is assumed only for this OMP profile.
- The mechanism depends on host kernel inotify semantics; exactness is claimed only for ledgers that report established, complete, non-overflowed marks. The three inotify sysctl limits are host conditions to be recorded with the host execution identity.
- **Open for owner acceptance (not decided here):** (i) workplan "Root-selection evidence contract" says burden claims are inadmissible "if the exact OMP build cannot expose that consumption"; this decision reads supervisor kernel observation plus observer-seen supply as an admissible exposure. On acceptance that bullet needs an `[Affected by …]` annotation (adopted, pending independent check: a marker at that bullet and contract revision 10 §1 item 13, `PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md`). (ii) Contract §1 item 4 scores owner reads "from complete `resource_access` records"; ledger-derived consumption is a supervisor accounting record in the summary, not a normalized event. Acceptance must either route a contract amendment (normalized derived event, schema version, completeness accounting) or explicitly accept the accounting record as the owner-read source for this profile. Resolution adopted by the stakeholder, pending independent check: the contract amendment route (contract revision 10, §1 item 13 `package_access` event). (iii) The rehearsal gate is an **acceptance boundary** (item 8), not an open remark. Contract revision 12 (`PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md`) is the adopted resolution of (i) and (ii) under `STAKEHOLDER-DECISION-2026-10-04-PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER.md` (replacement semantics, the gate target, positive-evidence handling and the observation-boundary reading of the workplan's runtime-observation bullet), pending independent check.

## Reopen triggers

Reopen D3 if realization needs any new principal/channel/edge, if distinctive-content-or-path attribution cannot identify an opened file on a package shape the project ships, if the subject gains the ability to influence or suppress marks, or if the contract metric changes from consumed-bytes to something the ledger plus supply cannot decide, or if model-driven package scans or runtime rescans make the owner floor UNRESOLVED at a rate the replacement rule cannot absorb, or if the item 8 rehearsal gate fails (honest executor behaviour makes the byte question or the owner floor inexact at a rate the campaign aggregation cannot absorb), or if a package or runtime breaks a stated premise (a whole owner line of at least the floor length occurring in a non-owner file; hard links or several binds; a runtime that opens owner copies without the model acting). Turn-window attribution is adopted for whole-file content in item 4(iii); extending it to partial runs is the remaining pre-registered fallback to evaluate on reopen, and the alternative is claim-scoped inadmissibility.

## D4 acceptance boundary

Real OMP → trusted observer → harness/core → scorer path:

- (a) `bash cat` of an owner yields exact bytes and a positive owner read at its result sequence;
- (b) accesses whose content cannot be shown supplied (count/hash/grep/transform/`wc -c`) yield `INADMISSIBLE` for burden claims with the file named, **including when other package files with overlapping or byte-identical content were shown** (shared kernel block; twin owner copy);
- (c) non-read mutation, ledger overflow, missing ledger and ledger/native contradiction are rejected;
- (d) pre-request opens other than `SKILL.md` are rejected;
- (e) previous guard behavior for ledger-less adapters is preserved;
- (f) retained failed and earlier realizations stay append-only;
- (g) an entrypoint-only run (no tool call, listing only, or a size probe of the delivered root) with an exact ledger is `COMPLETE_ADMISSIBLE` for burden claims;
- (h) an unrelated unexplained open leaves `owner_floor_exact` true and `owner_read_observed` intact;
- (i) a ledger-less adapter keeps the process-execution guard;
- (j) the burden claim gate rejects a deterministic root selection whose delivery proof failed even when the ledger is exact;
- (k) owner copies are recognized by one rule (basename) in accounting, in the harness and in the adapter's native owner-read path;
- (l) **positive owner evidence is content-based:** owner lines of at least the floor length shown to the model before R2 are a definite FAIL, through a relative-path partial read as well as an absolute `cat`, and survive an inexact byte observation, ledger loss, timing loss and an unexplained owner open;
- (m) an owner open before R2 whose content is shown only after R2 is **not** a pre-R2 read: the floor is UNRESOLVED (the open is not provably post-R2) and the post-R2 display is an owner-load hit, never a FAIL;
- (n) a package-wide scan (`grep -rl`, native `grep`/`find`) that opens all owner copies and shows no content, and `wc -l <owner path>` before R2, leave the floor UNRESOLVED and replaceable, never a FAIL, and a command that merely names an owner path without opening it affects nothing;
- (o) an owner open whose window starts after R2 is provably post-R2 and leaves the floor PASS-eligible;
- (p) timing loss (divergence from the per-run baseline, bracket wider than its bound, heartbeat gap) makes `owner_floor_exact` false, taints later brackets, and never changes a positive FAIL or hit;
- (q) a legitimate post-R2 owner load that falls in a heartbeat gap or timing-loss bracket is an owner-load hit, not a FAIL;
- (r) an in-flight or background owner open and an open after the last request receive windows that contain their true time, retried requests share their original's position, and a late-drained pre-R2 open is not provably post-R2;
- (s) a twin read through a non-literal path with the whole file shown is explained, a partial read of a twin through a non-literal path is unexplained for bytes, and a shared block shown within the window never explains a different file's open;
- (t) owner-load hits need no exactness of other files;
- (u) subject-volume overflow is recorded as loss and its replacement discloses the cause;
- (v) the byte question and the owner floor are reported separately and each campaign aggregation follows item 4a and contract §1 item 13.
