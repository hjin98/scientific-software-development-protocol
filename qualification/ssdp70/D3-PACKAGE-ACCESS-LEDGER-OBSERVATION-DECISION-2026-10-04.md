## Gap (classified: D3, not D4)

Native `read` events and observer-captured tool-result text do not bound which package files an arbitrary subject process (`bash`, and native `grep`/`glob`) read. In a run of the real OMP runtime driven by a scripted local stand-in provider, the subject obtained the T7 owner via `bash cat`; the harness reported no owner read and root-only bytes yet `COMPLETE_ADMISSIBLE` (`OMP-STANDIN-20261004T171724Z-…/run`). The D4 guard that now makes such runs `INADMISSIBLE` (`OMP-STANDIN-20261004T172146Z-…/run`) prevents a false claim but cannot supply the exact observation the burden metric needs. The accepted graph does not say which principal observes subject-process package access, so a D4 choice would silently decide an architecture question.

## Decision

1. **Owner.** The *qualification supervisor principal* observes access to the installed protocol package. The package tree is already a supervisor-owned immutable input that the subject receives read-only (`/opt/ssdp/skills`). Observation is a supervisor evidence-capture duty ("run identity/evidence capture").
2. **Mechanism class (D4 may substitute an equivalent).** A kernel-maintained per-inode access record taken on the supervisor's own host-side package directories (Linux inotify marks on the installed tree: open, access, close, mutation, overflow, unmount). It records accesses by *any* process that reaches those inodes through any path or mount, with no cooperation from, or channel to, the subject. Directory marks report by parent dentry; they are equivalent to per-inode marks here only because the installed tree is one fresh copy exposed through one read-only bind with no hard links. That equivalence is a premise of this profile (a package with hard links or several binds reopens D3).
3. **Topology.** No new principal, process, socket, proxy, credential carrier or cross-principal communication edge. The subject gains no capability; the supervisor receives information only from the kernel about its own files. The subject cannot read, write or influence the ledger; a failure to observe is itself recorded. The supervisor heartbeat source of item 5 lives outside every path the subject can reach and adds no edge. Unchanged: provider-control observer scope, mediator ownership, MCP bridge, subject authority.
4. **Ledger = upper bound; supply = content that identifies the opened file.** The ledger bounds *which package regular files were opened*. A file counts as *consumed* only when model-visible tool-result text (hash-linked request bodies, via the existing observer chain) supplies content **that identifies that file**: (a) native `read` through the existing `consumption` rule; or (b) for process output, content that is **one** of: (i) a contiguous match (the whole file, or a run of at least the distinctiveness floor) that is *distinctive*, contained in no other file of the installed package; (ii) a contiguous match produced by an action whose own recorded input names the file's package path; or (iii) the file's **whole** content (at least the floor size), contained in a tool result delivered in the same turn as the open's event-time bracket (item 5). Route (iii) is what makes a byte-identical twin read through a non-literal path (`cd <root> && cat references/x`, a glob, a variable) explained: the model then holds that file's entire content. A shared block or a partial run of a non-distinctive file never explains an open by route (iii); sources shorter than the floor are explained only by (a) or (ii); content shown for a different, non-identical file never explains an open. Routes (i) and (ii) do not depend on ordering; route (iii) depends only on the mechanical bracket of item 5. An opened file with no such supply is **unexplained**. Unexplained access, ledger loss (overflow, lost mark, unmount, mutation, mark not established, read error, row-bound exceeded, missing artifact) or an observed-content/ledger contradiction makes the **byte** observation not exact, and a not-exact byte observation makes T1/T7/T8 burden claims `INADMISSIBLE` (never a lower-bound PASS). Files never opened are *exactly* not consumed: a run whose root was delivered at request 0 with no further package access is an **exact entrypoint-only observation** (bytes = the delivered root `SKILL.md`), and a post-request re-open of a root whose full content was delivered is explained by delivery.
4a. **Exactness is per question; positive evidence is never suppressed; an owner access must be targeted.** Three questions have separate exactness. (A) The **byte question** (burden) needs every opened file explained (`exact`); `active_ssdp_bytes` is null unless `exact`. (B) The **owner-access question** (was any owner copy accessed, when; the zero-tolerance owner false-activation floor) needs the ledger intact and the timing of item 5 intact (`owner_access_exact`), whatever happened to unrelated files. (C) The **owner-load question** (hits after R2, which require the owner's content to reach the model) needs every opened owner copy explained (`owner_load_exact`): a hit is counted only for demonstrated supply, and an unexplained owner open leaves that hit unresolved, not missed. **Targeted owner access** is the only positive evidence of (B): (1) a native `resource_access` event; (2) the first open of an owner copy that is explained at file level (supplied by route (i), (ii) or (iii) of item 4 at any point in the trace, so `wc -l owner` before R2 followed by a later `cat owner` is explained and its *first* open counts); or (3) an open of an owner copy whose package path is named in the recorded input of a tool action delivered within the open's candidate window (item 5; for a turn-ambiguous open, any candidate turn), even if no content was shown. An owner open that is none of these is an **untargeted owner open** (for example a package-wide `grep -r`/native `grep`/`find` scan that never names the owner path and shows none of its content): it is *not* positive evidence and leaves (B) unresolved for that run, because absence of an owner read cannot be concluded; it is replaceable under the contract's replacement rule. The summary always publishes `owner_read_observed`, the set of targeted owner-access points (as windows, item 5) derived from native events, supply events and named opens, and `owner_untargeted_opens`, the opened owner copies that were not targeted. A targeted owner access whose window **ends** before the first predeclared R2 event is a **definite** zero-tolerance FAIL whatever the byte, owner-access and owner-load exactness; one whose window contains R2 is ambiguous R2 timing (unresolved, independently adjudicated); one whose window starts after R2 is post-R2. "No owner read" may be concluded only when `owner_access_exact` and no untargeted owner open exists; with neither a definite positive nor that conclusion the run is UNRESOLVED for that floor. Campaign-level owner false activation is unresolved only for runs in that state; unrelated unexplained opens elsewhere do not void it. Burden claims need `exact`; owner no-read conclusions need `owner_access_exact` and no untargeted owner open; owner-load hits need `owner_load_exact`. (`owner_read_exact` of revisions 2 and 3 splits into (B) and (C).)
5. **Phase split by request 0, a mechanical event-time bracket and candidate windows.** Opens before the hash-linked request-0 record are runtime-initiated (the model cannot act before it has a response). They are explained only when they are `<root>/SKILL.md` entries (catalog/activation); any other pre-request open is unexplained. Model-driven reads cannot precede the response, so opens at or after request 0 must be explained by supply or delivery. The cut is the observer's request-0 record stamp, taken after the full request body is read and before it is forwarded; **request 0 is the first subject-conversation request**, and auxiliary requests classified by the contract's frozen properties (contract §1 item 12) are not request 0 and do not delimit turns. **Ledger stamps are drain times, never earlier than the event, and draining can lag arbitrarily under supervisor contention; a drain stamp is therefore not an event time, and no lag bound is assumed.** The ledger carries a **mechanical ordering** instead: a supervisor-owned heartbeat source, outside every path the subject can reach, in the same kernel queue (one inotify instance keeps events from several watched directories in kernel order), with unique heartbeat names, so that each package event lies between two consecutive heartbeats. The event's real time then lies in a **bracket** whose lower edge is a stamp taken before the earlier heartbeat's write and whose upper edge is a stamp taken after the later heartbeat's write; scheduler or GIL lag can only widen a bracket, never make it wrong. D4 may use an equivalent mechanical ordering; an assumed lag bound is not equivalent. Heartbeats record `CLOCK_REALTIME` and `CLOCK_MONOTONIC`; a divergence beyond a declared tolerance, a bracket wider than a declared bound, or a heartbeat gap is **timing loss**, which makes (B) not exact (targeted positive evidence stands, as windows). The observer stamps requests with `CLOCK_REALTIME`, so every bracket edge is widened by the declared clock tolerance before use. Timing is expressed as a **candidate window** of trace events: its start is the first trace event after the last request stamped before the bracket's lower edge, and its end is the last trace event before the first request stamped after its upper edge (the end of the trace if there is none), so an in-flight or background open, an open after the last request and a timing-loss open (whose window runs from the first post-request-0 event to the end of the trace) all receive a window that contains the true time; an open whose window spans more than one turn is **turn-ambiguous**. An open is *pre-request* if its lower edge precedes the cut and *post-request* if its upper edge is at or after the cut (a straddling open is both). The zero-tolerance rule uses the window as stated in item 4a (definite only when the window ends before R2). Counted bytes depend on supply (items 4 and 6), not on phase; timing affects only phase classification, route (iii) and owner-access placement.
6. **Counting; owner-access placement.** Active SSDP bytes remain the contract metric: the root `SKILL.md` delivered/read plus each package file whose content reached the model (item 4), each counted once at full installed size; a byte-identical twin counts only when it was itself supplied or explained by route (iii). Native `read` behavior is unchanged. **Owner-access placement.** The placement of a targeted owner access is the candidate window of item 5 of its first open (a native event or a supply event is placed at its own sequence). Explanation is **per file**: the first open of an owner copy is judged explained if the file's content was supplied at any point (content already supplied cannot be supplied again, so no consumption is lost); route (iii) for a turn-ambiguous open accepts any candidate turn, which is lenient only where the whole file reached the model anyway. Owner copies are every package file whose basename is the owner's; the exactness of (B) additionally assumes that no non-owner file carries owner material (verified for the shipped package: no owner line of 48 bytes or more occurs in any non-owner file; a package where one does reopens D3). The parameters that decide results (the distinctiveness floor, clock tolerance, bracket-width bound, heartbeat period and gap bound, row bound, and the mark-lifetime bounds) are frozen in the execution profile before runs and recorded in the derived record; they are D4-delegated values, not D3 constants.
7. **Adapter scope.** The ledger is an adapter-produced supervisor artifact bound into the evidence-integrity chain. **Premises:** the supervisor opens no package file while marks are live and the marks outlive sandbox teardown (inotify records no pid, so a supervisor or observer open is indistinguishable from a subject open and would be unexplained or, if the owner, untargeted). Its rows fold repeated events per (file, flags) with first/last bracket and count and are bounded, so subject access volume cannot grow the record; the bound being exceeded is ledger loss. The fold is a declared **reduction that is lossless for these oracles**, not the raw kernel stream: phase, first-open time and byte accounting need only first/last brackets and counts. An adapter that produces no ledger keeps the previous behavior: process execution makes burden/owner claims `INADMISSIBLE`.

8. **Rehearsal gate (required before any adapter/profile using this ledger is admitted for a burden, owner-access or owner-load claim).** The independent pre-run checker runs an executor rehearsal through the exact adapter/profile **for each arm's package shape** (the 7.0 candidate and the 6.6 and 6.5 comparators, which differ in file count and twin structure; the shape at this revision is 238/63/38/213, 212/62/37/187 and 198/60/35/173 for files/distinct/twin groups/twinned files), covering at least: native `read` of a skill URL and path; `bash cat` with an absolute path; `cd <root> && cat references/x`; glob, brace, variable and loop paths; `head`/partial reads through literal and non-literal paths; `grep -r`, native `grep`/`glob` over the package; `wc`/`grep -c`; a command mixing a successful read with a failing command; a multi-turn run with compaction or other runtime rescan of the package (a rescan that opens owner copies would be a false owner access); and a **timing-stress form** with supervisor CPU contention. It reports, per form, per arm and for each of the three questions of item 4a, the exactness, the cause and the **verdict** (definite FAIL, targeted-but-not-definite, untargeted/UNRESOLVED, none), so that honest package scans are seen as an UNRESOLVED rate rather than hidden by exactness, and the bracket-width distribution. Because demonstrating a very small per-run rate statistically is infeasible (about 1,500 clean honest runs bound it at 0.2%), the gate is **structural plus reported**: the common honest forms must be exact by construction, and the remaining inexact forms and their reported rates are judged against the campaign target of the stakeholder decision `STAKEHOLDER-DECISION-2026-10-04-PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER.md` (probability at least 0.8 that no owner-unresolved run voids the campaign, with replacement allowed), which the independent checker instantiates for the owner floors **and for each burden route** (T7 with its pair-addition rule) from the frozen run count N, the aggregation rules (any run unresolved on the owner-access question leaves that floor unresolved; any inexact burden run leaves the fixed-cost part unresolved) and the replacement rule. Until the target is instantiated the gate is unmet and no such claim is admitted. Replacement semantics are owned by contract §1 item 13, not by this decision.

## Considered and rejected

- Remove `bash`/native process tools: contradicts the preserved 6.6 allow classes for T1/T7/T8.
- Observation via a FUSE or proxy filesystem serving the package: a new service and cross-principal edge; reopens D3.
- Content-matching alone: cannot prove absence of reads (a model can transform output); retained only as supply evidence.
- Conservative claim-scoped inadmissibility only: remains the fail-closed fallback, but forfeits a feasible exact observation inside the accepted graph.

## Residuals and non-claims

- Execution of arbitrary subject processes remains unauditable by pid; attribution is by identity of the supplied content or by the action's recorded path, not process identity.
- A read whose output is transformed (hash, base64, count) or scanned without being shown (`grep -c`, `grep -l`, `wc`, `grep -r … | head`, native `grep` over the package) is *unexplained*, so the byte question is not exact and the burden claim is conservatively inadmissible; this is intended. The owner-access question is isolated from it (item 4a).
- Tool results with error status are not supply even when the model saw the content (stricter, conservative). A stray non-zero exit (`cat a; cat missing`) therefore makes the shown file unexplained.
- **Shipped package shape.** The generated package at the time of this revision has 238 files with 63 distinct contents; 213 files are in 38 byte-identical twin groups, including the owner (seven copies) and every reference file. Distinctive content therefore identifies almost nothing. For process-read references attribution rests on a literal package path (route (ii)) or on whole-file same-turn delivery (route (iii)); honest non-literal forms that show the whole file (`cd <root> && cat references/x`, globs, brace expansion, shell variables, loops) are explained by (iii). Partial reads of a twin through a non-literal path (`cd … && head -n 40 references/x`) and any unshown read remain *unexplained*, so the byte question (and owner-load) is inexact; the owner-access question is not affected. This is fail-closed, not unsound.
- Path linkage tests that the input names the file, not that the action opened it. An action that names a twin while showing the other twin's identical content, or (route (iii)) a same-turn open of a twin whose whole content was shown for the other twin, explains the unshown open and counts it. The model then holds that file's entire content, so the file is correctly counted as consumed, but the same bytes can be counted twice and add an apparent second owner read. Over-counting is conservative on the candidate arm against its bounds, but it also inflates the 6.5/6.6 comparator denominators of the 2.0x and median-plus-bounds comparisons; the direction depends on the arm. It never under-counts the candidate's consumption.
- Untargeted owner opens (package-wide scans, a runtime rescan, transformed or hidden reads that do not name the owner) are not positive evidence and leave the owner-access question unresolved and replaceable, so they cannot produce a false FAIL. The cost is a **detection hole**: a model that systematically reads the owner by a form we cannot target (non-literal path, no content shown) is repeatedly UNRESOLVED instead of FAIL; the contract's replacement cap, the disclosure of every original and the per-arm inexact-rate bound limit what replacement can hide, and the multi-turn rehearsal measures the untargeted rate. In a real OMP run (stand-in provider, seven requests) a `grep -rl` over the package opened all 238 files including the seven owner copies with no owner content shown; compaction and long sessions are untested.
- A subject can fill the kernel queue by access volume (observed: 16,385 events with 9,000 opens while undrained), which is recorded as overflow loss. Overflow is therefore replaceable only with its cause disclosed and counted in the per-arm inexact-rate.
- The distinctiveness floor in item 4 is a D4-delegated minimum block size (48 bytes at this revision), not a D3 constant.
- Whether other adapters/runtimes can realize an equivalent observation is unresolved; no claim is made for them. Package root layout `/opt/ssdp/skills/<root>/...` is assumed only for this OMP profile.
- The mechanism depends on host kernel inotify semantics; exactness is claimed only for ledgers that report established, complete, non-overflowed marks. The three inotify sysctl limits are host conditions to be recorded with the host execution identity.
- **Open for owner acceptance (not decided here):** (i) workplan "Root-selection evidence contract" says burden claims are inadmissible "if the exact OMP build cannot expose that consumption"; this decision reads supervisor kernel observation plus observer-seen supply as an admissible exposure. On acceptance that bullet needs an `[Affected by …]` annotation (adopted, pending independent check: a marker at that bullet and contract revision 10 §1 item 13, `PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md`). (ii) Contract §1 item 4 scores owner reads "from complete `resource_access` records"; ledger-derived consumption is a supervisor accounting record in the summary, not a normalized event. Acceptance must either route a contract amendment (normalized derived event, schema version, completeness accounting) or explicitly accept the accounting record as the owner-read source for this profile. Resolution adopted by the stakeholder, pending independent check: the contract amendment route (contract revision 10, §1 item 13 `package_access` event). (iii) The rehearsal gate is an **acceptance boundary** (item 8), not an open remark. Contract revision 11 (`PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md`) is the adopted resolution of (i) and (ii) under `STAKEHOLDER-DECISION-2026-10-04-PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER.md` (replacement semantics, the gate target, positive-evidence handling and the observation-boundary reading of the workplan's runtime-observation bullet), pending independent check.

## Reopen triggers

Reopen D3 if realization needs any new principal/channel/edge, if distinctive-content-or-path attribution cannot identify an opened file on a package shape the project ships, if the subject gains the ability to influence or suppress marks, or if the contract metric changes from consumed-bytes to something the ledger plus supply cannot decide, or if model-driven package scans or runtime rescans make the owner-access question unresolved at a rate the replacement rule cannot absorb, or if the item 8 rehearsal gate fails (honest executor behaviour makes the byte, owner-access or owner-load question inexact at a rate the campaign aggregation cannot absorb), or if a package or runtime breaks a stated premise (a non-owner file carrying owner material; hard links or several binds; a runtime that opens owner copies without the model acting). Turn-window attribution is adopted for whole-file content in item 4(iii); extending it to partial runs is the remaining pre-registered fallback to evaluate on reopen, and the alternative is claim-scoped inadmissibility.

## D4 acceptance boundary

Real OMP → trusted observer → harness/core → scorer path: (a) `bash cat` owner yields exact bytes and an owner-read sequence; (b) accesses whose content cannot be shown supplied (count/hash/grep/transform/`wc -c`) yield `INADMISSIBLE` for burden claims with the file named, **including when other package files with overlapping or byte-identical content were shown** (shared kernel block; twin owner copy); (c) non-read mutation, ledger overflow, missing ledger and ledger/native contradiction are rejected; (d) pre-request opens other than `SKILL.md` are rejected; (e) previous guard behavior for ledger-less adapters is preserved; (f) retained failed and earlier realizations stay append-only; (g) an entrypoint-only run (no tool call, listing only, or a size probe of the delivered root) with an exact ledger is `COMPLETE_ADMISSIBLE` for burden claims; (h) an unrelated unexplained open leaves the owner-access question exact and `owner_read_observed` intact; (i) a ledger-less adapter keeps the process-execution guard; (j) an owner open before R2 whose content is shown only after R2 yields an owner-access sequence at or before the R2 event, while an unrelated open of a non-owner file does not, and this holds when the open is drained late (supervisor contention) because the bracket, not the drain stamp, fixes the turn; (k) the burden claim gate rejects a deterministic root selection whose delivery proof failed even when the ledger is exact; (l) owner copies are recognized by one rule (basename) in accounting, in the harness and in the adapter's native owner-read path; (m) positive owner evidence before R2 survives an inexact byte observation, ledger loss and an unexplained owner open, and is a FAIL, not UNRESOLVED; (n) a twin read through a non-literal path with the whole file shown is explained, a partial read of a twin through a non-literal path is unexplained, and a shared block shown in the same turn never explains a different file's open; (o) timing loss (clock divergence, bracket wider than its bound, heartbeat gap) makes the owner-access question not exact while leaving positive evidence; (p) the byte, owner-access and owner-load questions are reported separately and each campaign aggregation follows item 4a; (q) a package-wide scan (`grep -rl`, native `grep`/`find`) that opens all owner copies and shows no content leaves the owner-access question unresolved and replaceable, never a FAIL; (r) `wc -l <owner path>` before R2 (path named, nothing shown) is a targeted open and a definite FAIL when its window ends before R2; (s) a legitimate post-R2 owner open that falls in a heartbeat gap or a timing-loss bracket is ambiguous R2 timing, never a definite FAIL; (t) a background or in-flight owner open and an open after the last request receive windows that contain their true time (the window start is the first event after the last request stamped before the lower edge); (u) subject-volume overflow is recorded as loss and its replacement discloses the cause.
