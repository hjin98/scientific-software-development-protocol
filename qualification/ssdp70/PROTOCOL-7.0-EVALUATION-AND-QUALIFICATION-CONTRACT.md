# Protocol 7.0 evaluation and qualification contract

This is a Stage A evidence contract under the single consolidated handoff, not protocol authority. The handoff's §11.3 case/disposition list and §§11.4–11.6 semantic floors govern; this file freezes the numerical choices and execution/custody method **before any Protocol 7 candidate evaluation run**. A missing or contaminated required case is not a pass. Candidate changes after a run make affected evidence development data and require fresh blind qualification. No concrete fixture, planted key, answer, or human-trial answer is recorded here.

## 1. Exact subjects, arms and custody

- **Candidate:** exact Stage F immutable semantic commit and generated Protocol 7 packages, identified before runs. Any earlier Stage A/D draft is not a run subject.
- **Comparator:** accepted Protocol 6.6 canonical/public source and generated package resolved through `PROTOCOL-RELEASE-STATE.yaml` and the accepted 6.6 cutover. The fixed-cost denominator is instead fresh paired accepted-6.5 runs as the stakeholder decided; these two comparisons answer different questions.
- **Execution profile (portable).** Qualification is runner/vendor/environment agnostic. Before runs freeze an **execution-profile key** containing every exposed/controllable material condition: agent/model identity; provider/runtime and exposed version/build; reasoning/thinking configuration; runner-adapter identity; material workspace/environment realization where exposed; install mechanism; budgets; capability-manifest digest; isolation/containment-policy digest; network/external-write policy; credential/service-account policy; and every material provider-managed setting that cannot be fixed. Unknown/provider-managed values are recorded, never guessed, and preclassified as arm-neutral stochastic/provider-managed state or materially uncontrolled/not demonstrably arm-neutral. The latter makes a pair inadmissible for claims sensitive to it; a known provider/model/runtime migration inside a pair invalidates that pair. A matched pair uses the same execution-profile key except protocol arm. Local CLI, cloud agent, hosted workspace, container, VM or equivalent execution is permitted. Verify every run's runtime-visible catalog has its arm's SSDP skills exactly once and no other arm's SSDP skills. An isolation or profile-matching failure voids that run.
- **Custody:** the candidate author writes this framework and source but sees no concrete Protocol 7 fixture, key, expected answer or human-trial answer before the affected candidate freeze. A separate fixture-custodian context writes and holds those items and writes no candidate doctrine/source. The executor receives only blinded task artifacts. An independent evaluator receives keys only after the frozen run output. A separate pre-run checker authors neither candidate nor fixtures and checks the contract, withheld classification rationale, oracle branches and opportunity exposure before any candidate run. Access and contamination logs are required; author exposure converts the affected case to development data.
- **Scope:** use two or three composite scientific fixtures, each with a clean holdout and several blind properties. The custodian combines the handoff §11.3 cases across them without omitting any discriminating variant. It supplies matched O2-only and O3-bound authorizations and a genuinely excluded surface. No solution-bearing history is in executor-accessible artifacts.

**Portable runner-admission contract.** The Stage F qualification core owns subject identity, frozen cases/floors, execution-profile identity semantics, pair scheduling, custody/admissibility state, semantic capability classes, normalized event schema, required evidence/scoring manifests and scoring. Environment-specific adapters own only native realization and translation. The existing Claude-oriented Python scripts are one adapter/prototype, not normative execution architecture. An adapter may not redefine a capability class, omit a required event/item, substitute a weaker proxy or create an adapter-specific scoring path.

Any adapter/profile may be used only after the independent pre-run checker demonstrates all of the following through that exact adapter/profile:

1. **Exact subject and profile identity.** Immutable repository+commit subject resolution and source/package stamp verification; immutable commit plus package digest in run/evidence/cache identity; and the frozen execution-profile key above. Provider-managed unknowns follow the arm-neutral-versus-uncontrolled rule above. Known runtime/provider migration inside a pair invalidates the pair.
2. **Fresh arm isolation.** Exactly one copy of every SSDP skill, no ambient competing arm, fresh run-owned or equivalently isolated state, and independent state across concurrently executing pairs.
3. **Versioned semantic capability manifest.** Every native capability maps to one or more core semantic classes with `ALLOW`, `DENY` or `SANDBOX/MEDIATE` plus scope. Required classes cover: catalog/skill discovery and explicit root activation; workspace read/search/list; workspace create/modify/delete/rename/mode/symlink; process/command execution; delegation/subagent launch; issue/evidence-store read/search/write; repository/version-control or object-store operations that can cross the workspace boundary; network/remote-service access; external writes/mutations; and credential/secret/service-account access. An unrestricted code/process capability is admissible only when substrate containment still enforces file/network/credential policy. A denied class may have no unmediated equivalent escape route.
4. **Complete raw/equivalent trajectory and normalized event stream.** Private chain-of-thought is not required. The retained execution record must expose every observable needed by the frozen oracles. Every normalized event has schema version, run id, monotonic sequence/event id, actor id, semantic event kind, native-source reference, status and exposed timing. Required kinds/payloads are:
   - `catalog_snapshot`: logical skill ids, exact arm/package identity and multiplicity;
   - `root_selection`: selected logical root, entry stratum and activation mechanism (item 12), and resolved package identity. For deterministic entry it also carries the delivery record: installed `SKILL.md` SHA-256, the frozen delivery transform's identity and the delivered-text SHA-256, the hash-linked observer record of the first provider request, the byte offset of the delivered text within it, and the hash-bound runtime-input record (item 12);
   - `resource_access`: read/search/list operation, complete logical resource identity, full query/action input, result status and result/artifact reference;
   - `tool_action`: semantic capability class(es), native operation identity, complete action input or lossless artifact reference, start/result/error status and output reference;
   - `delegate_call` / `delegate_return`: stable delegate id, parent actor, complete request, result/reference, launched-work relation when observable and delegate capability/profile identity where material;
   - `issue_evidence_access`: store identity, operation, query/object ids and before/after object version for mutation;
   - `mutation`: create/modify/delete/rename/mode/symlink or equivalent, logical target, workspace/external class, authorization decision, blocked/sandboxed/live disposition and before/after identities where applicable;
   - `network_external_action`: destination/service identity at the granularity exposed, operation, authorization decision, blocked/sandboxed/live disposition and result;
   - `termination`: completed/error/timeout/turn-cap/cancelled/etc., native return state and whether a terminal result exists;
   - `final_result`: final report/result artifact identity and hash/reference;
   - `usage_timing`: monotonic/wall duration and provider usage units when exposed, with unit/source and explicit unknowns;
   - `package_access` (derived, supervisor-owned; item 13): the supervisor package-access observation for a profile that provides one.
   No oracle-relevant field may be truncated. Owner reads are scored from complete `resource_access` identity/action records, never from a reduced/truncated summary; for package access by process execution in a profile that provides the item 13 observation, the `package_access` event is the complete record and is scored under item 13.
5. **Raw-to-normalized completeness.** The adapter records a completeness map from every native observable action/event capable of affecting a required oracle to normalized event id(s), and classifies every unmapped native event. An unclassified/unmappable native event capable of affecting a required oracle makes the run inadmissible. Counts/hashes or equivalent linkage must detect dropped, reordered or truncated oracle-relevant events. Reduced summaries are convenience views only. A supervisor package-access ledger artifact (item 13) is a declared reduction, lossless for the item 13 oracles, of the kernel observation stream (rows folded per file and flags with first/last bracket and count, plus heartbeat records): the completeness map maps the artifact to the `package_access` event, and the file rows, loss and timing-loss conditions and counts of the event must reconcile with the retained artifact.
6. **Required evidence and scoring manifests.** Before runs the core freezes immutable run-bound `required_artifacts`, `required_oracles` and `expected_scoring_items` manifests. The scoring manifest contains stable item id, measure, criticality, applicable case/branch and allowed dispositions. A valid assessment contains exactly one disposition for every expected applicable item, no duplicates and no unknown item ids. Unresolved applicability is an explicit `UNRESOLVED` item, never omission. Every required artifact and required oracle must be present and validated; complete deterministic-oracle stdout/stderr or lossless artifact references are retained.
7. **Fail-closed states.** Evidence state is separate from process transport status: `COMPLETE_ADMISSIBLE`, `INADMISSIBLE`, `MISSING_REQUIRED_EVIDENCE`, `MALFORMED_EVIDENCE_OR_ASSESSMENT`, `EXECUTION_ERROR`, or `UNRESOLVED`. Qualification outcome is separately `PASS`, `FAIL`, `UNRESOLVED` or `NOT_EVALUATED`. Only `COMPLETE_ADMISSIBLE` evidence may enter PASS/FAIL scoring. A process that launched/exited successfully may not be surfaced as semantic `ok` when evidence is incomplete or inadmissible. Missing terminal result, required artifact/oracle, required scoring disposition or malformed assessment is non-PASS by construction.
   - **Evidence accounting scope.** Before launch, every realization declares its purpose: `qualification`, `oracle-integrity` (§6), or `development`. Purpose, campaign/suite identity and applicable scoring-manifest identity are immutable run/assessment provenance (item 11). The frozen campaign manifest enumerates qualification subjects and required exposure; the frozen integrity-suite manifest enumerates probes, deliberately introduced faults, expected evidence/criterion states and expected rejection or acceptance. The independent pre-run checker verifies their separation and completeness. No post-exposure reclassification or omission of a declared qualification run is permitted.
   - **Two assessments, one production scoring path.** An integrity probe exercises the same production admission/scoring path and criterion aggregation used for qualification, with a probe-local run/criterion scope. Its actual evidence state and criterion result are retained unchanged. The outer integrity check passes only when these match the predeclared expectation, including the required failure of a probe-local criterion for a broken input. An expected rejection is a successful integrity test, never admissible qualification evidence. An unexpected result, missing branch or missing assessment blocks qualification through harness/admissibility. This uses the existing manifests and scorer; it does not authorize a substitute test scorer or weaker oracle.
   - **Campaign aggregation.** Only `qualification` realizations enter campaign activation counts, exposure, doctrine floors, pooled counts, burden, comparative claims and human-trial evidence. Integrity and development realizations support no such outcome or exposure. A genuine undelivered deterministic qualification run fails the campaign activation criterion directly even though its evidence is inadmissible; this failure record is not PASS/FAIL doctrine scoring on inadmissible evidence. Expected injected faults in predeclared integrity probes do not fail that campaign criterion. Every unplanned integrity-probe failure still blocks the pre-run gate until independently resolved and the affected suite rerun, without changing or erasing its record.
8. **Containment and side effects.** Capability enforcement plus an isolated sandbox/VM/container/cloud workspace, audited proxy/service boundary, qualification-owned stand-in/test endpoint or equivalently strong mechanism must block a prohibited live external effect before it occurs or redirect it to qualification-owned isolated state while retaining the attempt. Logging a real prohibited live mutation afterward is not containment. Regex-only command matching is insufficient.
9. **Custody.** For machine qualification, fixture keys/answers are outside executor-reachable capability and credential scope until frozen run output. Pre-run checker/evaluator access is role- and time-scoped. Local directories, cloud object stores, secret mounts or hosted workspaces are permitted only when executor denial is demonstrated through the exact adapter/profile **and** access audit is demonstrated. Where the host provides no mechanical read-audit (for example a single-UID local host), the stakeholder may accept, as a recorded profile-scoped residual, a **behavioral access attestation** instead of the mechanical audit for **non-executor roles only**, provided: (a) executor denial is demonstrated both structurally (the recorded containment realization binds no custody, credential or host HOME path) and behaviorally by the exact profile’s own tool results; (b) each non-executor role’s access is role- and time-scoped and attested in writing by the stakeholder or the role, naming the paths opened; (c) frozen-tree integrity is shown by `FREEZE.sha256` verification and metadata comparison before and after each role; and (d) the residual that reads are unauditable is stated in every admission and qualification report that relies on it. Audit-only behavioral non-access remains no substitute for machine executor denial, and the human-trial exception in §7 is unchanged. The stakeholder adoption and pending independent-check boundary are recorded in `STAKEHOLDER-DECISION-2026-10-04-PROTOCOL-7.0-NON-EXECUTOR-CUSTODY-AUDIT.md`.
10. **Pair scheduling.** Arm execution is sequential inside each matched episode/replicate pair; independent pairs may execute concurrently only in independent state. Replicate and actual arm order participate in run identity.
11. **Evidence/cache provenance.** Bind subject commit/package digest; fixture/stub/oracle identities; execution-profile key; qualification-core/harness digest; normalized-event-schema version; adapter/normalizer digest; capability-manifest digest; required-artifact/oracle/scoring-manifest digests; replicate and pair order; purpose and campaign/suite accounting identity (item 7). Every primary-family run and assessment also binds the frozen campaign record, family-record digest and primary-family id (§1 item 12). Assessment reuse additionally binds evaluator identity/model/runtime/reasoning where applicable, evaluator-wrapper version, rubric/key digest and assessment-schema version. Executor-run cache and assessment cache may be separate, but each must bind every material dependency of the artifact it reuses. Integrity/development evidence and assessments cannot be reused as qualification evidence. A run with a package-access ledger also binds the ledger artifact digest, the package-access accounting code digest and the governing package-access decision's document path, commit and SHA-256 as recorded by its independent acceptance (item 13); a revision label alone is not an identity.
12. **Entry strata and activation mechanism.** Every run declares, before launch, one entry stratum and one activation mechanism. Both are part of run identity, and the mechanism is part of the execution-profile key. Recorder derivations D1–D4 are in decision record §5; D5 is in §6. Contract operationalizations are labelled R-op. Stakeholder answers Q1–Q5 are in decision record §§6–7.
   - **Deterministic entry** operationalizes the stakeholder's "standard command activation" (decision 2a). The declared root's entrypoint must reach the model before its first request, independent of any model choice. Two mechanisms are admissible:
     - **`runtime-command`.** The runtime itself expands the user's command. It is admissible only for a runtime and mode where the pre-run checker has demonstrated expansion through the exact adapter/profile (§6). Modes that pass the command through as text do not qualify. Examples are OMP print mode and Codex `exec` (`STAGE-7-RUNTIME-COMMAND-ACTIVATION-PROBE-RESULT-2026-10-04.md`).
     - **`harness-injection`.** The adapter places, in the first provider request, the same delivered text that the same runtime's demonstrated `runtime-command` produces at the provider-request layer. That covers the same role, position, invocation notice, transformed body and skill-directory line, and how the user prompt is joined.
       - It is admissible only for a runtime with a demonstrated `runtime-command` delivery form. A runtime without one, such as Codex `exec`, has no deterministic stratum.
       - A harness-injection result supports a delivery claim only. It does not support the claim that this runtime's user command loads the skill.
   - **Delivery transform and per-run proof.**
     - **The transform.** For each runtime and mode, the pre-run checker freezes a *delivery transform*. It is a deterministic function whose inputs are:
       - the installed `SKILL.md` bytes;
       - the user prompt;
       - the declared fixed skill-directory path (for the qualification sandbox, `/opt/ssdp/skills/<root>`);
       - declared runtime constants.

       Its output is the delivered segment as it appears in the decoded provider message content, after JSON decoding of the request body. For example, OMP RPC strips YAML frontmatter, prepends an invocation notice, and appends the skill-directory line and the prompt. Any other adapter-supplied text in request 0 must match a frozen template.
     - **Request 0.** The first provider request that carries the subject conversation. Auxiliary requests, such as title generation or model discovery, are excluded. They are classified by request properties fixed in the frozen transform specification (endpoint, purpose marker, position), never by whether skill text appears in them.
     - **What a run must show.**
       - Request 0, as captured by the trusted on-path observer and hash-linked, contains the transform's output for the declared root, at a recorded offset.
       - The adapter's **runtime input** is retained and hash-bound into the evidence-integrity chain. It means the invocation channel only: argv, stdin or RPC messages, prompt-bearing environment variables, and any prompt or command file. A prompt-bearing variable is one whose value the runtime or adapter incorporates into the subject conversation or command input. The §6 checker verifies this channel classification and that variables outside the template and runtime configuration supply no entrypoint-derived text to that conversation. The installed skill package, fixture workspace and runtime configuration are environment realization, already bound by their own identities (items 1 and 11), and are not part of the runtime input. Credential values remain excluded from retained records under the credential policy; their identities and non-prompt role are attested without persisting the secret.
       - For `runtime-command`, the runtime input must equal a frozen input template rendered from the command, the fixture prompt and the declared constants. For `harness-injection`, it must equal the injection template rendered with the delivered segment.
       - Request 0 together with the runtime input determines the mechanism. A mechanism mismatch is an activation failure.
     - **What does not count.** Runtime events and adapter delivery records only corroborate. A model-initiated read never establishes delivery.
     - **Runtimes without the observer.** A runtime whose provider requests cannot be observed this way is claim-scoped inadmissible for the deterministic stratum.
   - **Activation failure.** These are activation failures:
     - request 0 lacks the delivered text, carries another root's text, or does not match the transform;
     - a mechanism mismatch;
     - a run that ends before any conversation request.

     Such a run is `INADMISSIBLE` for every floor. It also **fails the deterministic-activation criterion for its profile** (§3); rerunning it cannot rescue that failure.
     - Requalifying the profile requires all of the following:
       - a recorded root cause attributing the failure to the adapter or harness;
       - an independently reviewed repair that removes that cause;
       - a new profile key, a fresh §6 pre-run check and a fresh full campaign.
     - An undiagnosed failure, or one caused by the runtime, falsifies `runtime-command` for that runtime and mode. Re-keying cannot cure it.
     - Reports disclose every earlier failed campaign of the profile lineage.
     - The failed campaign stays on record.
   - **Ordinary entry** has no command and no injection. Under stakeholder decision 2b, made conditional by Q2, it carries no floor on activating. The condition is met by any qualification that satisfies the Q1 requirement below, which every PASS must.
     - Ordinary runs are reported per profile in four groups:
       - no selection;
       - wrong root;
       - admissible root (`ordinary-read`);
       - prose-instructed (`instructed-read`).
     - The report covers at least three ordinary episodes per arm for each of the run, ad hoc analysis, results-review, gate-evidence, copy/transcribe/relay and delegate classes. That exposure is recorder-chosen for a report-only measure (D2).
   - **Retained false-activation floors (stakeholder Q4).** These floors stay binding:
     - selection false activations on the 6.6 negative selection cases and the near-boundary negative episodes (§4), both of which are ordinary-entry runs;
     - predicate false-firing (§4), scored on every run where an SSDP root was delivered or selected, in either stratum. This includes ordinary near-boundary runs that wrongly select SSDP. The scope is a recorder choice (D5). The §4 bound's denominator counts every predicate-excluded opportunity so scored, and its minimum of 12 must be met on the deterministic stratum alone;
     - zero owner false activations on every run in either stratum (unchanged, D4).
   - **Run-type strata.**
     - **Deterministic, each with a custodian-predeclared root:**
       - every §11.3 semantic case, including composite fixtures, O1 authoring and review, tension retrieval and delegate cases;
       - the T2/T3 sentinels, T4–T6, T1/T7/T8 and the P01–P19 routing probes;
       - the R2 owner-load opportunities;
       - the predicate-excluded opportunities;
       - the outputs shown in the §7 human trial.
     - **Ordinary:**
       - the 6.6 selection routes S01–S11/H01–H05, whose correct-selection bound is report-only (stakeholder Q3);
       - the 6.6 negative selection cases and near-boundary negatives (floors retained);
       - the new-class activation episodes above (report-only).
     - Matched arms share stratum and mechanism.
   - **Scoring scope.**
     - The doctrine floors and the comparative claim are evaluated on the deterministic stratum. That stratum must meet every §2 exposure minimum on its own.
     - The deterministic-activation criterion and the retained false-activation floors apply as stated.
     - Ordinary runs enter no other floor. Every critical failure in them is listed in the report, by group.
   - **Primary flash profile family and profile coverage (stakeholder Q1, Q5).** Where this bullet goes beyond the quoted answers, it is a recorder operationalization, labelled R-op.
     - **Before the candidate's first campaign:** the offered profile set is frozen in the campaign record, and one flash-class **primary profile family** is designated.
       - *Flash-class* means the stakeholder-designated default campaign executor (currently `deepinfra/zai-org/GLM-5.3-Flash`) or another model the stakeholder designates in writing before runs.
       - The family is a predeclared set of execution-profile keys (R-op) that share model, runtime and mode, reasoning, adapter and containment. They differ only in entry mechanism and panel-required capabilities and budgets. The panel budget schedule is frozen in the family record; selection retains the 6.6 select mode / 3-turn cap, route probes the 8-turn cap, and trajectories the 60-turn cap unless a separately reviewed governed change replaces them. Matched arms within each panel share its key and budgets. For example, T1/T7/T8 has no delegation:
         - **deterministic keys** use `runtime-command` for every deterministic run;
         - **one same-model ordinary-entry key** hosts the ordinary runs.
     - **Criterion-to-key map.** Before runs, the family record maps every part of each §3-ordered criterion, including exposure and report-only measures, to the family key or keys that evaluate it (R-op). The following are minimum required assignments, not an exhaustive map:
       - doctrine floors, critical judgments and the comparative claim: the main deterministic key;
       - burden: the T1/T7/T8 deterministic key for the §4 fixed-cost backstop and no-lookup oracle; the main deterministic key for the §4 class-iii/new-class active-material bound and all §5 bounds, including the minimum 12 eligible delegate parts, zero unowed reads/probes and report-length/time medians;
       - the human trial: outputs from the main deterministic key;
       - the Q4 false-activation floors on ordinary negatives: the family's ordinary-entry key.
       - harness/admissibility: all family keys;
       - deterministic activation: all deterministic keys;
       - remaining deterministic 6.6 preservation: P01–P19, T2/T3, T4–T6 and each R2 owner-load class, each assigned to its declared deterministic panel key;
       - S01–S11/H01–H05 correct-selection reporting and the new-class activation episodes: the ordinary-entry key;
       - pooled predicate false-firing and owner-false-activation counts: all family keys, with the predicate-excluded exposure minimum met on deterministic keys alone.
     - **Pooled counts.** Predicate false-firing (D5) and owner false activations are pooled across the family's keys. This pooling is the family's predeclared aggregation under the profile-scoped result rule, and it can only add failures, never remove one.
     - **The family result** is `PASS(primary-family-id, candidate, comparator-set)` or a non-PASS state. The family id hashes the ordered set of its keys and the criterion-to-key map.
       - Before the first run, the campaign record freezes the complete family record (ordered keys, panel budget schedule, full map including exposure, aggregation rules and family id) and its digest. The record specifies the exact serialization and hash algorithm used to reproduce the id and digest. The independent §6 checker verifies these bindings and exposure on every mapped key before runs; each run and assessment binds them under item 11. A changed record is a new revision requiring a fresh pre-run check and affected requalification, never retrospective remapping of existing outputs.
     - **The primary family must reach `PASS` on every §3-ordered criterion** (stakeholder Q5):
       - harness/admissibility;
       - deterministic activation across every declared root;
       - no critical failure;
       - every absolute floor;
       - 6.6 preservation, including the Q4 floors on its ordinary-entry key;
       - burden;
       - the comparative claim;
       - the §7 human trial.
     - **Blocking (R-op).** The *final criterion-level* state of each criterion counts, after the replacements, reruns and adjudications that §§4–5 and §7 allow. Any non-`PASS` final state (`FAIL`, `UNRESOLVED`, `NOT_EVALUATED`, inadmissible, missing evidence, or claim-scoped-out) blocks qualification PASS for every profile. A run-level state blocks only through the criterion it leaves non-PASS. The exception is an undelivered deterministic run, which fails the activation criterion directly. Here, claim-scoped-out means inability to expose a required property. Contract-permitted, predeclared descriptive-only routes with fewer than three episodes (§5) and a named-class-only comparative claim (§3) are claim limits, not non-PASS criterion states; they neither waive mandatory exposure/floors nor conceal a failure.
     - **Other offered profiles** are additional strata. They may use `harness-injection` and must meet the activation criterion on their own (D1). They never rescue the primary, and none can be withdrawn after runs start. The §7 human trial runs on the primary family only; other profiles carry no human-legibility claim. A single deterministic-key PASS on another profile carries no claim about ordinary-entry selection false activations: those Q4 floors are established only on the primary family's ordinary key. It must still meet predicate false-firing and zero owner false activations on its own scored runs, without importing the primary's counts. Every reported non-primary PASS states these limits explicitly.
     - **Changing the primary family** needs a written stakeholder decision before the next campaign.
       - A requalification re-key under the root-cause rule above is not a change of family only when every family-shared field and the frozen panel capability/budget schedule stays fixed except the independently reviewed repaired adapter/harness identity. This includes model, runtime and mode, reasoning and containment. It is recorded as a new family revision.
       - Every earlier campaign of this candidate and of earlier Protocol 7 candidates under this workplan is disclosed, whatever its outcome.
   - **Record.** `PROTOCOL-7.0-ACTIVATION-STRATA-CONTRACT-AMENDMENT-2026-10-04.md` (revision 8).

13. **Package-access observation (process-executed package reads; contract revision 14, labelled R-op where it operationalizes a stakeholder rule).** Native read events and observed tool-result text do not bound which installed-package files an arbitrary subject process (`bash`, native `grep`/`glob`) read. A profile whose subject can run such processes therefore must be a **ledger profile** or a **no-ledger profile**, as follows; the remaining bullets of this item apply to a ledger profile.
   - **Ledger profile.** The qualification supervisor, not the subject and not a new principal or channel, observes access to the installed package for the lifetime of the subject run and the adapter produces a retained **package-access ledger**. The mechanism class is delegated. Attribution of opened files to content that reached the model, owner-class supply and the owner-floor rules, the phase split at request 0, the mechanical event-time bracket and candidate windows, the exactness values, the rehearsal gate and the probe set are owned by the governing D3 decision `D3-PACKAGE-ACCESS-LEDGER-OBSERVATION-DECISION-2026-10-04.md` at the revision accepted by independent D3 acceptance; this contract does not restate them. A change to that decision, to this item or to the §6 ledger paragraph is a joint change and requires fresh independent acceptance of all.
   - **No ledger.** Any process-execution event leaves the package read set unobserved: burden (T1/T7/T8) and owner-read claims for that run are claim-scoped `INADMISSIBLE`; no lower-bound byte total and no negative owner-read conclusion is published. A native pre-R2 `resource_access` owner read still scores as positive evidence.
   - **The `package_access` event.** For a ledger profile the core derives, after the run and deterministically, exactly one `package_access` event (actor: supervisor; status `observed`) from the retained ledger artifact, the normalized events and the immutable installed package. It carries without truncation: the ledger artifact SHA-256, schema and mechanism; whether marks and heartbeats were established and every loss and timing-loss condition (overflow, lost mark, mutation, unmount, read error, row bound exceeded, missing or malformed artifact, clock divergence from the per-run baseline, bracket width, heartbeat gap); the request-0 cut and the request stamps used; the frozen parameters that decide results (distinctiveness and owner-line floor, the owner-load quantum, clock tolerance, bracket-width bound, heartbeat period and gap bound, row bound, mark-lifetime bounds); for every opened regular file its package-relative path, size, SHA-256, per-interval first/last event-time bracket, count, read/open-only distinction, phase relative to request 0 and explanation (`delivered`, `supplied` with the supplying event ids and the attribution route, or `unexplained`); for every opened owner copy its candidate window; the owner-class supply and native owner reads with their result sequences; and the derived `exact`, `owner_floor_exact`, `owner_read_observed`, `owner_minor_exposure`, `owner_open_windows`, reasons and, only when exact, the active-byte total. An independent evaluator must be able to recompute the event from the retained artifacts; a mismatch makes the run inadmissible.
   - **Claim scope.** A burden run is scored only from an exact observation: a run for which `exact` is false never publishes a byte total (no lower-bound value) and is `INADMISSIBLE` for the burden claim; a *route* may still resolve from other runs under the unknown-value rule of the *T7* and *Replacement* bullets, which is a bound on the route and not a lower-bound total (see the *T7* and *Replacement* bullets). **Owner floor (§4 zero-tolerance floor and owner-load hits).** An owner read keeps its meaning, content that reached the model, and is scored under the governing D3 decision's item 4a (owner-class supply and native reads at their own trace sequences; the owner-load quantum; minor exposure; UNRESOLVED and replaceable where a negative cannot be concluded). **Positive evidence is never suppressed (stakeholder decision above):** a read before the first predeclared R2 event is a zero-tolerance FAIL whatever the byte exactness, ledger loss or timing loss, and a read after R2 is an owner-load hit needing no exactness of other files. Ambiguous R2 timing remains unresolved and independently adjudicated (§4).
   - **Campaign effect (clarification of the fail-closed rule, item 7).** A qualification run that is `UNRESOLVED` on the owner floor, or `INADMISSIBLE` for a burden claim only because the observation is not exact, keeps that floor or part, and the campaign criterion, non-PASS unless the slot is resolved under the rules below.

The replacement is a §5 rerun (at most two independent reruns per affected case, no outcome threshold changes) and is **the scored run for every criterion** of that slot. The original is never removed: both identities are recorded, its cause is disclosed, its outcomes are disclosed but not counted, and per-arm and per-form inexact-run and replacement counts are reported. In the median comparison the unknown value of a candidate-arm run is taken as unbounded above and that of a comparator-arm run as zero, so unknown candidate runs sort to the top and comparator runs to the bottom; the route's bound resolves `PASS` only if it holds under that adversarial assignment, otherwise it is `UNRESOLVED` (reporting the mixture and the interval). The original stays on record, and its persistence keeps the mixed-mode trigger on through the added pairs to the seven-pair stop. **A T7 run that is `UNRESOLVED` on the owner floor** (it has no positive owner evidence) may be rerun **solely to resolve the owner floor**: that rerun does not enter the T7 median, the original stays an unknown value for the burden route, and pair addition proceeds as above; a T7 run with positive owner evidence is never replaced.
   - **Rehearsal gate.** Before a ledger profile is used for a burden or owner claim, the independent pre-run checker runs the executor rehearsal required by the governing D3 decision (its item 8) through the exact adapter/profile, for each arm's package shape and for both questions. Without an instantiated target and a met gate, ledger-dependent claims remain `INADMISSIBLE` or `UNRESOLVED` as above.
   - **Record.** `PROTOCOL-7.0-PACKAGE-ACCESS-LEDGER-CONTRACT-AMENDMENT-2026-10-04.md` (revision 14).

## 7. Human legibility trial and ratification evidence

**Participant (stakeholder decision 2026-09-28, `STAKEHOLDER-DECISION-2026-09-28-PROTOCOL-7.0-SINGLE-PARTICIPANT-HUMAN-TRIAL.md`).** The single participant is the stakeholder, as the reader the workplan's §11.6 minimum names. **Exposure.**

- The stakeholder reviews **exactly one fixture per arm**. The two fixtures are different, so the same fixture is never seen in both arms, and the other arm's output on either fixture is never seen.
- With one participant, counterbalancing is impossible. The custodian therefore fixes before exposure, by a recorded random draw, which fixture serves which arm and which arm comes first.

**Floors.**

- **Per arm:** no materially wrong critical answer caused by the material, and at least 80% correct routine answers (≥16/20 at minimum exposure).
- **Across arms:** candidate-arm median time to answer at most 2.0 × the baseline arm's median time.

Unanswered questions and misleading interpretations count as wrong. A blinded independent evaluator scores the answers against the frozen expected answers.

**Exposure accounting and non-completion.** Exposure is counted by questions **presented**, not questions answered.

- An observed floor failure stands whether or not the trial is completed.
- Non-completion makes the trial non-discriminating only when its recorded reason is unrelated to the material, such as unavailability or a harness fault. In that case it is never a pass.
- Otherwise every presented question left unanswered is scored wrong.
- A question set that presents fewer than 20 routine or 4 critical questions in either arm is underexposed and never a pass.
- A non-discriminating trial may be repeated only on fixtures the stakeholder has not seen, under a fresh custodian draw. The earlier observations stay in the record.

**Record** assistance, arm unblinding, the arm order and the time. Unblinding is near-certain, because the participant is also the ratifier and knows the Protocol 7 doctrine; the ratification package states this.

**Stated limitation.** A pass establishes intended-reader legibility **for the stakeholder as reader only**, on the one drawn fixture per arm and the one drawn arm order. It makes no claim about other readers, other fixtures or a reader population. Fixture difficulty is confounded with arm, including in the time ratio, which compares different fixtures; matched question templates reduce but do not remove this. The ratification package states these limits.

**If the trial cannot run,** release acceptance remains blocked; no machine proxy or ratification narrative substitutes. The ratification package reports denominators, failures, comparator, limitations and residual findings, not a PASS label alone.
