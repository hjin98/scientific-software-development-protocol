## Blockers by earliest owner

### D3 (decision revision 6)

**D3-B1. Request position in the trace is undefined, and the conservativeness claim rests on it.** Items 4a and 5 define the candidate window as "trace events from the first event after the last subject-conversation request stamped before the bracket's lower edge...", and "provably post-R2" as "the first trace event of its candidate window follows the R2 event". Requests are observer records with `t_ns` stamps; they are not events in the normalized sequence. In `adapters/omp.py`, observer requests are classified (`observer-inference-request`) and only request 0 yields a normalized event (`root_selection`). Tool results carry `result_request_index`, but assistant-text and tool-start events carry no request linkage, and native events carry no wall time (only some assistant records have `completedAt`). So "the position of request k in the trace" has no definition, and "any imprecision errs toward UNRESOLVED" cannot be checked. Realizable, for example by pairing the k-th subject-conversation inference request and response records with the k-th native assistant turn, but D3 must freeze the mapping primitive, its direction (earliest consistent position), and the fallback (not derivable means start of trace). This is the central test of the owner floor; leaving it to D4 silently decides a correctness question.

**D3-B2. Request stamps are not required to be monotone; a backward wall-clock step can produce a false PASS-eligible.** Timing loss is detected from heartbeat divergence against the per-run baseline, and taints brackets "from the first divergent heartbeat onward". Request stamps are never checked. Take a pre-step owner open with a clean bracket (both heartbeats before the step). Requests issued after a backward step carry numerically smaller stamps, so under "last request stamped before the lower edge" a post-step request can be selected, which moves the window start later than the truth and can make a pre-R2 open provably post-R2. This is a path from clock step to false PASS-eligible, which the text claims cannot exist. Repair: request stamps must be non-decreasing in conversation order and consistent with the heartbeat baseline, else timing loss; and state that the window is determined by trace order, not by numeric stamp comparison alone. Also state the bracket at the ends: a heartbeat must precede subject launch and follow the last possible event (or sentinel), else timing loss; today an open before the first or after the last heartbeat has no defined bracket.

**D3-B3. Owner-class supply is ambiguous in two places that decide FAIL versus UNRESOLVED.**
(a) Residuals bullet "Tool results with error status are not supply even when the model saw the content" is stated for byte supply, but it is unscoped. If read as applying to owner-class supply, `cat owner; false` or `cat owner && false` hides a pre-R2 read from the FAIL path for free. Item 4a says "a tool result seen by the model", which implies error results count. State explicitly that owner-class supply counts error-status results and that the exclusion is byte-supply only.
(b) Matching granularity. "A contiguous run of whole owner lines of at least the floor length" does not say whether the owner line must be a whole output line or may be a substring of an output line (`cat -n`, `grep -n`, `nl` prefix the line), nor whether the floor applies to a single line or to a run of short lines. I checked both: on the shipped candidate package, 0 of 242 owner lines of 48 bytes or more occur in any non-owner file as a whole line, and also 0 as a substring of any non-owner bytes; no run of consecutive short owner lines totalling 48 bytes or more occurs in a non-owner file either (0 of 37 minimal runs; only the empty line is shared at all). So the premise holds under every reading on this package, but the decision should state the reading it means (substring of an output line, single line or run) so the D4 implementation and the premise check test the same thing.

**D3-B4. Stale or inaccurate statements in the decision.** (i) Parents line still says "evaluation contract rev8 §1 items 4-5, §4, §6"; the governing contract is now revision 12 with item 13. (ii) Open-items bullet (46) still names "contract revision 10, §1 item 13" twice (as the adopted resolution) before pointing to revision 12; superseded revision named in a current-state sentence. (iii) Item 39 says the owner and "every reference file" are in twin groups; `software-implementation/references/debugging-and-state-recovery.md` is a distinct, un-twinned reference file (25 singletons: 7 SKILL.md, 7 protocol-manifest.json, 7 openai.yaml, three templates, one reference). Harmless to the argument (it is distinctive, route (i)) but inaccurate. (iv) "27 shared sub-line runs of 48 to 117 bytes": my count with a 48-byte sliding window is 28 maximal runs, longest 123 bytes; the discrepancy is immaterial because the premise is not claimed at sub-line granularity, but the figure should be restated as approximate or recomputed.

**D3-B5. The rehearsal list omits the honest form that most threatens feasibility (see D3-F3), and has no premise-verification step.** Item 8 should add: (1) R2 event and owner load in the same assistant response, and parallel calls; (2) a mechanical premise check on the frozen candidate package (no whole owner line of at least the floor in any non-owner file; no byte-identical copy of the package reachable elsewhere in the sandbox; one bind, no hard links). The package shape and the premise are stated "at this revision" while Stage E will remeasure and regenerate the package, so the premise must be re-verified on the frozen bytes, not carried forward.

### Contract (revision 12)

**C-B1. Item 13 contradicts itself, and the stakeholder record, on replacement of non-T7 burden runs.** The Replacement bullet: an observation-inexact original "may be replaced under the §5 rule (at most two reruns per affected case; T7 is governed by the next bullet)". The next bullet (T7 and burden routes): "An observation-inexact burden run is not replaced; it is an unknown value ... triggers T7's pair addition". T1 and T8 have a fixed three-pair design with no pair addition in §4; class iii and the new §11.3 classes likewise. So for T1, T8 and the other burden routes the text gives two incompatible dispositions (replace versus unknown value with a pair-addition remedy that does not exist for them). The decision record repeats this: adopted decision 1 still says a burden run inadmissible only for inexact observation may be replaced (non-T7), while second-round (d) says an inexact burden run is not replaced; the record marks parts of the first round as superseded (confirmations 2 and 3) but not this. The disparity bound over "burden comparisons" has meaning only if burden runs can be replaced. Resolve explicitly per route class: for T7 unknown value and pair addition; for T1/T8 and class iii either (a) replacement under §5 with the disparity bound, or (b) unknown value with the same worst-case assignment and, if inexact runs cannot be added, UNRESOLVED; and mark decision 1 of the record as superseded to that extent. Also reconcile "Burden claims require `exact` ... never a lower-bound PASS" with the unknown-value rule, which can yield a route PASS when some runs are inexact (sound as a worst-case bound, since PASS requires the bound under candidate-unbounded and comparator-zero, but the sentence "never a lower-bound PASS" and the rule must be reconciled in the text). When the bound fails even under the best-case assignment the rule still says UNRESOLVED; a definite FAIL would be more informative and affects the §8.3 reopen path, but UNRESOLVED is conservative, so this is a note, not a blocker.

**C-B2. "The one declared change in effect" (§8, item 13 title, amendment §2/§5) is an understatement.** Effects that differ from revision 8 and are not declared as changes in effect: (a) process-executed owner reads become scorable owner reads (revision 8 scored owner reads only from `resource_access` records, so a `bash cat` of the owner was not scored at all); this widens, which is intended, but "no change in effect from rev 8" for the floor is not literally true; (b) the owner floor gains a new UNRESOLVED state (an owner open not provably post-R2), stricter than revision 8; (c) UNRESOLVED owner-floor runs become replaceable so that the replacement "resolves the slot", which goes beyond §5's "report unresolved rather than selecting the favorable run" (arguably within §5 because the original is an observation failure with no outcome, but the contract should say so); (d) a single inexact T7 run persists in its arm, so the mixed-mode trigger stays on through every added pair to the seven-pair stop (each inexact T7 run costs four extra pairs). Declare these in §8 as effects, with direction (stricter or looser), or state why each is within existing authority. No new outcome threshold, floor or exposure minimum was added; the 0.8 target and the frozen disparity bound are acceptance-process values correctly labelled R-op.

**C-B3. D3 is not the single owner of the owner-floor rule.** Item 13 states "this contract does not restate them", yet the Claim-scope bullet restates the no-read condition ("requires `owner_floor_exact` and that no owner copy was opened at a point that is not provably after R2 ... leaves the floor UNRESOLVED and replaceable, never a FAIL"), D3 item 8 restates the 0.8 target and aggregation that the contract owns, and the workplan §0.1 entry and two markers restate the same floor sentence. All are currently consistent, but each is a second site that must change in a joint change. Point instead of restating (contract: "scored under D3 item 4a"; D3: "target and aggregation owned by contract item 13"). Low severity; fix with the others.

**C-B4. Cross-reference hygiene.** Contract §8 and the amendment cite `/tmp/SSDP70-INDEPENDENT-CHECK-...` files that are not in the repository; a durable contract cannot rely on non-resolvable routes. Commit those reports or drop the paths. The "exactly one of" lead-in of item 13 lists nine bullets of which only two are alternatives; restructure so the lead-in governs only the Ledger/No-ledger pair. The disparity bound is "a per-arm bound on the difference in inexact-run rates" without saying which exactness (`exact` versus `owner_floor_exact`): the owner-floor UNRESOLVED can occur only on the candidate arm (comparators ship no owner copy), so a bound over arm differences is trivially violated if it counts owner-floor unresolved; define the measure per question.

## Findings that are not blockers (D3, for the repair revision or D4)

**D3-F1. Evasion of owner-class supply, and the detection hole.** Falsification: owner lines shorter than 48 bytes (67 of 409 lines, including the empty line) are invisible by design; a model that transforms output before display (`fold`, `cut -c`, `tr`, `awk substr`, `base64`, `sed` that strips leading whitespace of indented lines, `head -c` truncating a line, a Python print that reflows) fully informs itself while no whole owner line of 48 bytes or more reaches the tool result as a substring. Line splitting, paging (each page has whole lines, so paging does not evade) and content across several results (whole lines survive) are not evasion routes; transformation is. Such a read lands in UNRESOLVED (the ledger shows the open; the open is not provably post-R2), never in PASS, so the evasion cannot produce a false PASS in that run. It can, however, launder the floor via replacement: a transformed pre-R2 peek is replaced by a rerun, a visible peek is a FAIL and is never replaced. D3 states this detection hole honestly (residuals) and the decision record adopts no cap on replaced owner-unresolved runs beyond the per-case cap. Recommendation: stakeholder confirms that residual (below), and the rehearsal reports, per form, how often a transformed read still shows owner content.

**D3-F2. Owner-class supply on content that is not a deliberate owner read.** It never fires on the delivered root text, descriptions, or other package files on the shipped package (verified). It does fire on a single matching owner line shown by a package-wide `grep -rn`/native `grep` of a keyword, which stakeholder confirmation (c) ("partial owner content is supply") accepts; a pre-R2 keyword grep of the package that happens to match one owner line of 48 bytes or more is a definite, non-replaceable zero-tolerance FAIL. Also the premise is only verified over the package; owner-class supply scans every tool result, so fixtures, workspace files, stub-tool and MCP results and the task text must be checked for owner lines too (cheap mechanical pre-run check; add to D3-B5).

**D3-F3. Feasibility: honest owner load can leave the floor UNRESOLVED by construction.** The R2 event the workplan describes is an agent identification ("the agent's first identification of the affected reported results"), and a model commonly emits that text and the owner-read tool call in the same response. The open's window starts at the first event after the last request, which precedes the R2 text inside that response, so the open is "not provably post-R2" and, per boundary (m), the floor is UNRESOLVED even though the owner content is shown after R2 (the owner-load hit is still scored). Conservative and correct, but "the common honest forms must be exact by construction" (item 8) is then false for the main form the owner floor exists to allow, and the 0.8 target's UNRESOLVED rate on owner-load trajectories (six or more per class, at least eighteen in total) could be large. Depends on custodian R2 predeclarations (a tool-result R2 event in an earlier response is provable). Not decidable by text; add the form to the rehearsal (D3-B5) and note the existing reopen trigger.

**D3-F4. Owner floor needs timing only when an owner open exists.** `owner_floor_exact` is defined as ledger intact and timing intact. A run with no owner open but a heartbeat gap or wide bracket is UNRESOLVED on the floor, which costs replacements under supervisor contention for no benefit. Restating timing intactness as required only when at least one owner open exists is strictly a simplification and loses nothing.

**D3-F5. Fold per (file, flags, heartbeat interval): lossless and bounded, with one wording fix.** The oracles need only per-interval brackets (phase, windows, byte accounting). The fold loses counts exactness (the kernel coalesces consecutive identical events anyway) but nothing the oracles use. Interval keying means one owner copy can have several rows; "every opened owner copy with its candidate window" must be read as every row, because a pre-R2 scan row plus a later legitimate-load row must both be tested. State "for every owner row". Bound is files x intervals x flags and the row bound exceeded is loss; a subject can reach that loss by access volume (observed 16,385 events/9,000 opens per D3), which only yields replaceable UNRESOLVED/inexact, never a FAIL and never positive-evidence suppression (positive evidence is content-based).

**D3-F6. Route (iii) and the shared-block failure.** Route (iii) needs the whole file (at least the floor) inside one tool result in the window, so a shared block or partial run of a non-distinctive file cannot explain an open: free of the revision-1/2 shared-block failure. Per-file explanation loses no consumption. Residual correctly stated in D3: an unshown twin opened in a window where the other twin was shown is explained and counted, a double count that inflates comparator (6.5/6.6) denominators and so loosens the 2.0x bound in the candidate's favour for those runs. D3 says "direction depends on the arm"; at the contract level this should be reported per route in the rehearsal rather than left as a footnote, because it is the one remaining non-conservative direction for a burden PASS. Not a blocker.

**D3-F7. Realizability of the observation mechanism.** I ran an inotify probe in scratch space: two watches (package dir, heartbeat dir) on one inotify instance preserve kernel order across directories; unique heartbeat creations bracket package events; open/access/close are distinct (open-only, read, close-nowrite); an mmap read generates open and close but no access. The shipped package has 29 directories; host limits (524288 watches, 16384 queued events) are consistent with D3's overflow remark. The mechanism sketch is realizable. Not run: a real OMP run, because the D4 code at `8be024a` realizes revision 3 only, and a probe through it would not test revision 6.

## Answers to amendment record section 6

1. Owner-class supply identifies owner reads soundly on the shipped package (premise verified above, including the substring reading), and placing a positive read at its result sequence is free of timing assumptions for the FAIL direction. It can be evaded only by transformed output (D3-F1), which lands in UNRESOLVED; the hole is stated and bounded only by the per-case replacement cap and disclosure; confirm (below). Error-status results must be stated to count (D3-B3a).
2. The provably-post-R2 test is conservative on late drain (heartbeat ordering, no lag bound), heartbeat gap, in-flight/background opens and opens after the last request (window start after the last request), retries (shared position), auxiliary requests (excluded by item 12's frozen properties), and parallel calls (unresolved). It is not conservative for a backward wall-clock step (D3-B2) and its definition depends on an undefined request position (D3-B1). So: not yet.
3. Route (iii) is free of the shared-block failure; per-file explanation loses no consumption; the twin double-count residual is a comparator-denominator direction (D3-F6).
4. The `package_access` event matches D3's published fields and is derivable from the retained ledger artifact, normalized events (which carry `result_content`) and the installed package; the request stamps used are carried. Recompute additionally requires the request-position mapping (D3-B1) and the heartbeat records (retained in the artifact, mapped by item 5). The R2 identification is scoring data outside the event, which is acceptable. The fold is lossless for what the oracles need and bounded (D3-F5). Gaps: bracket edges at the start and end (D3-B2).
5. Item 13 gives no path to PASS when positive evidence exists (FAIL stands) and none to owner-floor PASS when `owner_floor_exact` is false. A burden route can PASS with inexact runs under the worst-case assignment; sound but must be reconciled with "never a lower-bound PASS" (C-B1). The gate target recorded as unmet until instantiated: correctly fail-closed. The campaign effect is a faithful clarification of item 7.
6. The T7 unknown-value rule is well defined for T7: unknown candidate runs sort to the top and comparator runs to the bottom, so the median of an odd count is defined (one unknown candidate run does not move a three-run median; two do); unknown owner-read mode counts as the mixed-mode trigger of §4; adversarial assignment is the worst case for both the 2.0x-versus-6.5 bound and the 6.6 + delta + owner + 512 bound; PASS only if the bound holds under it. It is not the only change in effect (C-B2), is undefined for T1/T8 and class iii (C-B1), and every inexact run keeps the trigger through seven pairs. Replacement exploitability: selection effect is real (inexactness correlates with scanning habits, the disparity bound limits arm asymmetry not outcome correlation; originals are retained and disclosed, but the contract does not say whether an original's non-ledger outcomes stay in other criteria's counts; state it); positive evidence is never replaced; overflow is subject-reachable but only produces replaceable UNRESOLVED, with cause disclosed; the fail-closed default is sound; the disparity bound's measure is undefined (C-B4).
7. Workplan entry and markers: consistent with the overlay convention except W-B1 and W-B2. Revision 8's criteria, family rule and activation-strata bytes: `git diff 15a2297 HEAD` on the contract changes only the front-matter status, item 4 (new `package_access` kind and one sentence), item 5 (one sentence), item 11 (one sentence), new item 13, one §6 paragraph and §8; items 1-3, 6-10, 12, §2-§5, §7 are byte-identical to revision 8; the workplan diff changes only the §0.1 entry and four marker insertions (no other text). So revision 8's criteria, family rule and activation-strata bytes are unchanged in effect, subject to C-B2. All cross-references resolve inside the repository except the `/tmp` report paths (C-B4) and the stale names in D3-B4. No document names a removed field (`owner_access_exact`, `owner_load_exact`, `targeted`/`untargeted` as live rules); they appear only in dated history and realization notes.
