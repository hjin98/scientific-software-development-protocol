## Gap and decision

Clarification A makes unpositioned upper bounds end at the trace end and otherwise empty windows cover the whole trace. With unverified request pairing, every request is unpositioned and every open can receive a whole-trace window. Route (iii) can then explain an opened byte-identical twin using whole content shown for its sibling anywhere in the trace. Counting that twin on a comparator can inflate comparator bytes and favor the candidate on comparative burden bounds. Conservatism of an owner-floor window does not establish conservatism of a comparative byte count.

**Decision: route (iii), whole-file supply within an open's candidate window, is available only when the run's request/assistant-turn pairing is verified by the existing canonical pairing primitive.** Failure to establish that condition denies route (iii) for every file and every open in that run. A whole-trace fallback window is not a substitute for verified pairing. No per-open or per-result verified subset rescues route (iii) in an unverified run.

This is the smallest change to the existing attribution mechanism: a precondition on its window-dependent route. It requires no new principal, input channel, clock, pairing algorithm or parallel validator/scorer.

## Canonical pairing primitive and fail closure

The canonical primitive remains D3 item 5's verified pairing, concretized by the adapter's normalization map. The existing production path is `eval/adapters/omp.py:request_positions` → retained bundle `request_records` → `eval/core70.py:derive_package_access` → `eval/package_ledger.py:account`. Function identities describe the current D4 owner and remain replaceable under equivalent semantics.

The primitive pairs the ordered subject-conversation inference requests with ordered native assistant turns, verifies their counts and correspondence, and verifies that the next conversation request carries the preceding assistant message and results. Auxiliary requests use the contract's frozen classification and do not create conversation turns; retained retries share their original conversation position. These are the existing verification duties, not a new partial matching rule. The adapter owns deriving verification and the complete conversation/retry record set from retained raw evidence. The accounting consumer uses that result; it does not independently invent or repair pairing.

For this delta, **verified pairing** means the canonical primitive successfully verifies the run, publishes its complete request records with `pairing_verified` as the literal Boolean `true` on every record, and those records remain bound to the retained observer/native evidence under the existing completeness and recomputation contract. A label supplied by a fixture, subject or unrelated summary does not establish qualification verification. A missing/empty record set cannot establish the precondition for route (iii); an omitted expected record cannot be hidden by requiring all remaining records to be true. Coverage belongs to the existing adapter/completeness owner.

The accounting gate must deny route (iii) for a missing pairing field, literal `false`, `null`, strings such as `"true"`, numbers such as `1`, inconsistent flags, malformed records or any verification/coverage failure. It must not coerce truthy values to true, infer verification from a numeric position, infer verification from an intact ledger/timing record, or default omitted metadata to verified. A malformed pairing record must not yield a route-(iii) explanation through an exception or fallback. Other evidence-invalidity conditions retain their existing fail-closed consequences.

**Verification and position are different primitives.** Under successful pairing, the position is the existing trace-order position, or `null` for a verified text-only turn with no tool event. That null position is valid and does not deny route (iii). Clarification A's lower/upper fallback and otherwise-empty-window rules continue to apply in that verified run. A value of the wrong type masquerading as a position is not a verified text-only null. The existing normalization map owns position validity; D4 must retain the distinction rather than inventing a new numeric-position requirement.

## Preserved boundaries and effects

- **Byte attribution.** Native consumption, delivered-root explanation and process-output routes (i) distinctive content and (ii) action input naming the file remain unchanged, including their floors and residuals. An open may still be explained through these routes when route (iii) is unavailable. Therefore unverified pairing alone does not force byte inexactness when every open is independently explained and all other exactness conditions hold. If an open has only route-(iii) evidence, it is unexplained; `exact` is false, `active_ssdp_bytes` is null, and the burden claim is `INADMISSIBLE`, with the file and denied-route reason retained. No lower-bound total is published.
- **Owner floor.** Positive native/owner-class supply stays at its result sequence and is never suppressed by denial of route (iii). A positive pre-R2 owner read remains a definite FAIL; a post-R2 positive remains a hit; the owner-line floor, quantum, minor exposure and conservative provably-post-R2 test are unchanged. Unverified pairing keeps the existing unpositioned window-start fallback and its UNRESOLVED consequence when an owner open cannot be proved post-R2. No extra owner-floor failure follows merely from this gate, and a no-owner-open run retains the existing negative-observation conditions.
- **Verified windows.** Verified text-only requests and existing verified timing-loss/in-flight/background/after-last-request windows retain their meanings. This proposal removes the specifically unverified-pairing route-(iii) path; it does not claim to remove the existing identical-twin residual for otherwise allowed windows. Rehearsal must still disclose that residual and its per-arm comparative direction.
- **Campaign and replacement.** Contract item 13 and clarification B remain the sole owners of replacement eligibility, adjudication, one scored run per slot, failures that stand, attempt cap, disparity bound and T7 unknown-value handling. Inexactness newly exposed by this gate enters those same rules. Observation-bound unresolved dispositions continue to block eligibility under retained R4-1; their intended future exception is not implemented here. Measure that loss in rehearsal. No failure is discarded and no additional rerun is granted.
- **Direction and availability.** Denying route (iii) removes unverified pairing as a source of twin-count inflation, including on comparator arms. It can increase inexactness and unavailable replacements on any arm; it makes no quantified rate or 0.8 gate-success claim before rehearsal.

On acceptance, this delta supersedes only clarification A's acceptance of route-(iii) whole-trace explanations for runs with unverified pairing, and the parent route-(iii) rule to the extent it permitted those explanations. It preserves A's window construction and verified text-only behavior and all of B. Pending acceptance, this is a visible proposed change, not an implicit rewrite of the passed parents.

## D4 acceptance delta

After independent D3 text Review and closure of the contract's joint-change acceptance requirement, implement at the existing accounting consumer and preserve the adapter's canonical verification/record coverage. Required evidence must exercise the real adapter → core derivation/recomputation → accounting → burden/owner scoring path; pure accounting fixtures may discriminate the gate but cannot establish adapter verification or campaign integration alone.

1. **Discriminating negative:** an opened non-literal twin whose sibling's whole content appears elsewhere in the trace is explained by route (iii) under the old whole-trace path; with failed pairing it must now remain unexplained, have null active bytes and an inadmissible burden claim. Exercise candidate and comparator package shapes. Also use an otherwise honest whole-file non-literal read: failed pairing still denies route (iii), even when that costs availability.
2. **Metadata negatives:** omit the field or all records; use false/null/string/numeric flags; mixed true/false rows; malformed rows/positions; a dropped expected conversation/retry record; mismatched counts, assistant correspondence or next-request history; a compaction, misclassified auxiliary request and retry mismatch. Demonstrate canonical verification/coverage rejection through its real owner, and deny route (iii) without truthy coercion, exception rescue or reliance on remaining verified rows.
3. **Positives:** fully verified pairing permits the existing non-literal twin whole-file-in-window explanation. A verified text-only final turn has `position: null` and literal true pairing; the honest preceding read remains explained under A. Verified retries retain the original position; correctly classified auxiliary requests do not invalidate pairing. Preserve existing lower/upper fallback, empty-window and timing-loss cases when pairing is genuinely verified.
4. **Independent explanation:** failed/missing pairing with distinctive route (i), valid path-linked route (ii), native consumption or delivered-root explanation preserves their outcomes; when these explain every open, the byte question can remain exact. A shared partial block still cannot explain a twin by route (iii), verified or otherwise.
5. **Owner/campaign separation:** with route (iii) denied, preserve positive pre-R2 FAIL, post-R2 hit and minor exposure; preserve the unverified owner-open UNRESOLVED fallback. Exercise actual burden scoring and the existing non-T7/T7 handling of newly inexact runs, including retained R4-1 replacement loss. No new replacement exception or cap is accepted by this test delta.
6. **Recomputation and retention:** retain request pairing flags, positions, underlying observer/native bindings, supplying event ids/routes and denied-route reasons in the existing run evidence/event. Recompute through the real core consumer; a supplied explanation disagreeing with raw verification cannot be accepted. Preserve old evidence bytes and identities. Run focused and complete affected adapter/core/accounting/scoring regression after the bounded code change; failing or unexecuted required checks remain blockers.

Rehearsal remains mandatory under D3 item 8 and contract item 13: report per-arm/per-form unverified-pairing rate, opens denied route (iii), resulting byte inexactness, replacement attempts/scored results and R4-1 lost replacements, plus the verified-window residual. Bind fresh evidence to the accepted delta and changed accounting/normalization bytes. Do not reuse an earlier exact byte claim that depended on unverified route (iii) as current proof.
