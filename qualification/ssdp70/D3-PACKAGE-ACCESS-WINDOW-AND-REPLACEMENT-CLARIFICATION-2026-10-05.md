# D3 package-access window-end and slot-replacement clarification

Governing SSDP 6.6.0; Protocol 7.0 NON-QUALIFIED. Bounded clarification of two points that the independent D4 Review (`INDEPENDENT-D4-PACKAGE-ACCESS-IMPLEMENTATION-REVIEW-2026-10-04.md`, finding 15 and finding 4) found undetermined by the accepted decision. Authorized by the stakeholder's acceptance of the recommendations ("I accept. Proceed.") on 2026-10-05. **Independent D3 text Review is required before this clarification governs D4 acceptance.** D3 revision 8 (`fccb9a3a…cd783`), the premise-closure clarification (`5f713e2b…a3316`) and contract revision 15 (`c08a3e65…e1920`) remain unchanged. No mechanism, principal, channel, capability, floor or threshold changes.

## A. Window end when a bounding request has no derivable position

**Gap.** D3 item 5 defines a candidate window from the first event after the last request stamped before the bracket's lower edge to the last event before the first request stamped after its upper edge, and says that an unpairable or unverifiable request position is "the beginning of the trace, which is the conservative case (it can only enlarge a window)". That is true for the lower side. A request that bounds a window from **above** and has no position (the usual case is a text-only final assistant turn, which has no tool call or result event; another is a failed pairing verification) would, read literally, end the window before the first trace event and leave it empty. An empty window can explain nothing, so an honest whole-file read followed by a text answer would be unexplained for the byte question depending only on which heartbeat interval the open happened to fall in.

**Clarification.** A request with no derivable or verified position bounds nothing **from above**: the window then runs to the end of the trace. Any window that is otherwise empty (end before start) is the whole trace. The lower side is unchanged: no earlier request, or an unpositioned earlier request, starts the window at the beginning of the trace. Window edges for opens with timing loss, in-flight opens and opens after the last request remain as in D3 item 5.

**Effects.** The owner floor depends on the window **start** only (an owner row is provably post-R2 only if the first trace event of its window follows R2), so it is unchanged. For the byte question, route (iii) can then accept whole-file content shown in a later tool result of the same trace. D3 item 6 already accepts this for windows spanning several turns ("lenient only where the whole file reached the model anyway"): the file is still counted once at its full size and was in fact consumed. The residual that a twin can be counted from content shown for its identical sibling is the one already recorded in D3 "Residuals".

## B. One slot, one scored run

**Gap.** Contract item 13 says a replacement "is the scored run for every criterion of that slot" and "resolves the slot only if it is exact for the question concerned", with at most two independent reruns per affected case. It does not say what happens when a replacement resolves one open question (for example bytes) but not another (the owner floor), nor which run then scores the other criteria.

**Clarification.** A slot has at most one scored run. A non-T7 replacement is the scored run for every criterion of the slot only if it is exact for **every available question still open on the original**. The owner floor is always available; the byte question is available only with the frozen disparity bound (contract item 13). A replacement that resolves only some of them is **disclosed and not scored** (its outcomes are disclosed but not counted, as for any replacement that does not resolve), the slot stays unresolved, and the second of the two allowed reruns must again resolve every available open question. Once a replacement is scored, any further rerun of that slot is outcome selection and is refused. With no frozen byte bound, a replacement is scored on the owner floor alone, the byte question stays pending on the original, and the criterion stays non-PASS as the contract already states. A T7 owner-floor-only rerun is unchanged: it answers the owner floor alone, stays outside the median, and the original remains the T7 burden value.

**Effects.** No mixing of doctrine criteria from one run with owner results from another; the two-rerun cap is used exactly as written; the rule fails closed. The cost is that a first replacement exact for only one of two open questions is wasted. That is a common shape (a package scan leaves both bytes and the owner floor open), so the rehearsal must report the rate of such partial replacements as an input to the 0.8 target.

## D4 acceptance delta and impact
D4 realizes A in two places: the adapter's `request_positions` publishes `position: null` for a turn with no tool event and for every request when the pairing is not verified, and `package_ledger.candidate_window` treats any non-integer position as unpositioned (lower side: the trace start; upper side: the end of the trace) and makes an otherwise empty window the whole trace, with deterministic tests of the honest text-final-turn form, an absent or unpositioned earlier request, and inconsistent positions. D4 realizes B in `batch_assess70.replacement_slots` with tests for partial-then-complete replacement, refusal of reruns after a scored replacement, the no-bound owner-floor case and the cap. Passed documents are not edited. At the next governed revision the D3 text of item 5 and contract item 13 can absorb both paragraphs. Reopen D3 if the rehearsal shows that the partial-replacement rate or the window-end lenience makes the 0.8 target or the byte-question exactness untenable.

Reader: independent D3 reviewer and the pre-run checker. Routine questions: what bounds a window from above when a request has no position; when does a replacement become the scored run; what happens to a partial replacement.
