# D3 package-access window-end and slot-replacement clarification

Governing SSDP 6.6.0; Protocol 7.0 NON-QUALIFIED. Bounded clarification of two points that the independent D4 Review (`INDEPENDENT-D4-PACKAGE-ACCESS-IMPLEMENTATION-REVIEW-2026-10-04.md`, finding 15 and finding 4) found undetermined by the accepted decision. Authorized by the stakeholder's acceptance of the recommendations ("I accept. Proceed.") on 2026-10-05. **Independent D3 text Review is required before this clarification governs D4 acceptance.** D3 revision 8 (`fccb9a3a…cd783`), the premise-closure clarification (`5f713e2b…a3316`) and contract revision 15 (`c08a3e65…e1920`) remain unchanged. No mechanism, principal, channel, capability, floor or threshold changes.

## A. Window end when a bounding request has no derivable position

**Gap.** D3 item 5 defines a candidate window from the first event after the last request stamped before the bracket's lower edge to the last event before the first request stamped after its upper edge, and says that an unpairable or unverifiable request position is "the beginning of the trace, which is the conservative case (it can only enlarge a window)". That is true for the lower side. A request that bounds a window from **above** and has no position (the usual case is a text-only final assistant turn, which has no tool call or result event; another is a failed pairing verification) would, read literally, end the window before the first trace event and leave it empty. An empty window can explain nothing, so an honest whole-file read followed by a text answer would be unexplained for the byte question depending only on which heartbeat interval the open happened to fall in.

**Clarification.** A request with no derivable or verified position bounds nothing **from above**: the window then runs to the end of the trace. Any window that is otherwise empty (end before start) is the whole trace. The lower side is unchanged: no earlier request, or an unpositioned earlier request, starts the window at the beginning of the trace. Window edges for opens with timing loss, in-flight opens and opens after the last request remain as in D3 item 5.

**Effects.** The owner floor depends on the window **start** only (an owner row is provably post-R2 only if the first trace event of its window follows R2), so it is unchanged. For the byte question, route (iii) can then accept whole-file content shown in a later tool result of the same trace. D3 item 6 already accepts this for windows spanning several turns ("lenient only where the whole file reached the model anyway"): the file is still counted once at its full size and was in fact consumed. Two consequences are stated explicitly because they are larger than for a normal window: (1) a run whose request pairing is **not verified** has every request unpositioned, so every one of its windows is the whole trace; (2) the residual already recorded in D3 "Residuals" (a twin can be counted from content shown for its identical sibling, so the same bytes can be counted twice) can then occur in any arm. It never under-counts the candidate; on the comparator arms it can raise the comparator byte count, which is the direction that favors the candidate on the 2.0x and median bounds. This is accepted as a bounded, disclosed residual, not a new mechanism; the rehearsal must report the rate of runs with unverified pairing and the per-arm effect on the byte question, and D3 reopens if either makes the byte comparisons untenable.

**Superseded wording.** For the upper side of a window this clarification supersedes D3 item 5's statement that the beginning-of-the-trace fallback "can only enlarge a window" and the "start of the trace" wording of D4 case (x); for the lower side they stand.

## B. One slot, one scored run

**Gap.** Contract item 13 says a replacement "is the scored run for every criterion of that slot" and "resolves the slot only if it is exact for the question concerned", with at most two independent reruns per affected case. It does not say what happens when a replacement resolves one open question (for example bytes) but not another (the owner floor), nor which run then scores the other criteria.

**Clarification.**
1. **One scored run.** A slot has at most one scored run. A non-T7 replacement is the scored run for every criterion of the slot only if it is exact for (a) its own **owner floor**, always, because it becomes the scored run for the zero-tolerance floor whatever was open on the original, and (b) the **byte question** when that question was open on the original and is available. The byte question is open on the original when its observation was inexact on a non-T7 burden slot; it is available only with the frozen disparity bound (contract item 13). With no frozen byte bound a replacement is scored on the owner floor alone, the byte question stays pending on the original, and the criterion stays non-PASS as the contract already states.
2. **A replacement that does not resolve is still a run, and no definite failure in any declared run is discarded.** If a replacement resolves only some of the questions of item 1 it is **not scored**, the slot stays unresolved, and the second of the two allowed reruns must again resolve all of them; its observation-dependent unresolved questions and its non-failing measurements are disclosed and not counted. A **hard failure** is a positive owner read before R2 (in any evidence state in which the core derives it, contract item 13 claim scope, stakeholder decision 3), a deterministic-activation failure, or a `fail` disposition. A **block** is a hard failure or an unresolved suspected O3, claim-integrity or mutation violation (any unresolved disposition; see the known limitation below), tested on a replacement exactly as contract item 13 tests an original before replacing it. A block in a replacement **stands for the slot**: the slot is scored on that run and stays non-PASS (or unresolved), and every further rerun of the slot is refused. It stands whatever the original's eligibility (an original that is unadjudicated, has undisclosed overflow or is unresolved on another criterion is itself not replaced, but a replacement declared for it still cannot hide a failure) and whatever the replacement's evidence state. An **original** with a hard failure stands and is never replaced: a replacement declared for it is an invalid campaign record (item 4). The deterministic-activation criterion counts every declared deterministic run, scored or not (contract section 3 and item 12): it fails if any declared run fails and passes only if every one passes. This closes the outcome-selection path of §5 (rerunning until a clean run).
3. **Cap and counting.** The cap of two independent reruns is per frozen `replacement_case` identity (one case may cover several slots; the T7 owner-floor-only rerun is capped per T7 run) and counts every attempt, scored or not. The per-arm and per-form counts report **attempts** (`replacements`) and **scored** replacements separately.
4. **Refusal.** A replacement declared for an original that has no open question it can resolve (a pre-declared reserve cannot override an original that needed no replacement; the byte question counts as open for this purpose whether or not the frozen bound makes it available), a replacement declared for an original that carries a hard failure, a rerun of a slot that already has a scored replacement (clean or standing failure), a third attempt, a reused replacement identity, or a replacement that changes the frozen profile or subject is an invalid campaign record: aggregation raises and produces no result, so no partial scoring can be mistaken for a campaign outcome.
5. **T7.** An owner-floor-only rerun is unchanged: it answers the owner floor alone, stays outside the median, and the original remains the T7 burden value. A block in it stands as in item 2: a positive pre-R2 owner read counts for the owner floor, a deterministic-activation failure fails the activation criterion, and its `fail` dispositions count in the critical-failure and disposition tallies, although the run stays outside the median.
6. **No frozen byte bound.** The byte question stays pending on the original and the byte total stays that of the original (exact or not); the scored replacement supplies the owner floor and every other criterion. This is the contract's rule that, absent a frozen bound, replacement for the byte question is unavailable.

**Effects.** No mixing of doctrine criteria from one run with owner results from another; no discarded failure; the two-rerun cap is used exactly as written; the rule fails closed. The cost is that a first replacement exact for only one of two open questions is wasted. That is a common shape (a package scan leaves both bytes and the owner floor open), so the rehearsal must report the rate of partial replacements as an input to the 0.8 target.

## Known limitations carried to the next governed revision (not decided here)
Found by the independent text Review (R4); none creates a false PASS, each costs availability or leaves an integrity condition to the custodian:
1. **Observation-bound dispositions.** The aggregation requires every opportunity, including the owner-floor, fixed-cost and active-material parts, to bind a scoring item, and an evaluator is told to return `unresolved` for an item it cannot resolve. An original whose only unresolved item is bound to those parts is therefore treated as having another unresolved criterion, so it is not eligible and its mandatory replacement is lost (fail closed). The intended rule is that dispositions bound only to owner-floor, fixed-cost and active-material opportunities on an observation-inexact run do not block; it is not implemented because it needs the manifest's opportunity binding in `other_criteria_clear`, `observation_adjudicated` and `blocks_rerun`. The rehearsal must report how often this loses a replacement.
2. **Unbound declared runs.** A run declared in the campaign manifest that is neither opportunity-bound nor a recorded replacement is scored nowhere. The manifest is custodian-frozen; the pre-run checker should reject such a declaration, or aggregation should count it.
3. **T7 owner-only rerun.** A critical disposition that is `unresolved` (not `fail`) in a T7 owner-only rerun is counted nowhere.

4. **Line truncation of process output (rehearsal item).** The code review found that the OMP `bash` tool truncates output lines at 768 characters, so whole files with longer lines can never be explained by route (iii) (66 of the 213 twinned files of the shipped package shape). An honest whole-file read of such a file leaves the byte question inexact and the burden slot replaceable. The rehearsal must report this rate per arm; D3 reopens if it makes the burden comparisons untenable.

## D4 acceptance delta and impact
D4 realizes A in two places: the adapter's `request_positions` publishes `position: null` for a turn with no tool event and for every request when the pairing is not verified, and `package_ledger.candidate_window` treats any non-integer position as unpositioned (lower side: the trace start; upper side: the end of the trace) and makes an otherwise empty window the whole trace, with deterministic tests of the honest text-final-turn form, an absent or unpositioned earlier request, and inconsistent positions. D4 realizes B in `batch_assess70.replacement_slots` with tests for partial-then-complete replacement, a partial, unusable-evidence or failing replacement carrying a positive pre-R2 owner read, against an eligible, unresolved, unadjudicated and overflowed original (through `score_slots`, not only `replacement_slots`), a deterministic-activation failure or a critical `fail` disposition including in a T7 owner-only rerun, refusal of a replacement declared for an original with a definite failure, a failing or unresolved disposition in a replacement, the replacement's own owner floor, refusal of reruns after a scored replacement, the no-bound owner-floor case, the cap and the attempt/scored counts. Passed documents are not edited. At the next governed revision the D3 text of item 5 and contract item 13 can absorb both paragraphs. Reopen D3 if the rehearsal shows that the partial-replacement rate or the window-end lenience makes the 0.8 target or the byte-question exactness untenable.

Reader: independent D3 reviewer and the pre-run checker. Routine questions: what bounds a window from above when a request has no position; when does a replacement become the scored run; what happens to a partial replacement.
