## 1. Verdict

**NO-PASS.** One narrow SERIOUS CHALLENGE to the D3 window/replacement clarification (it is realized correctly by D4, so it is a rule defect, not a code defect), and two D4 blockers in `batch_assess70.py`. The ledger core is sound: I found **no trajectory that gives `owner_floor_state` PASS although owner content reached the model before R2**, and I found **no honest run shape that depends on heartbeat phase** (details in section 6). The blockers are in replacement and slot scoring, which is where the author's recent changes landed.

### SERIOUS CHALLENGE SC-1 (route to the D3 text owner; narrow, one sentence to repair)

`D3-PACKAGE-ACCESS-WINDOW-AND-REPLACEMENT-CLARIFICATION-2026-10-05.md` (sha256 `924194c4…2ca4`, section B) says a replacement that resolves only some available open questions is "disclosed and not scored (its outcomes are disclosed but not counted)". Contract item 13 and D3 item 4a say a positive owner read before R2 is a zero-tolerance FAIL "whatever the byte exactness", that positive evidence is "never suppressed", and §5 says to report unresolved "rather than selecting the favorable run". These conflict for one sub-case: a first rerun that is byte-inexact but shows a positive pre-R2 owner read (a definite FAIL) is unscored by B, and a second rerun that is exact and PASS then becomes the slot's scored run. Executed on the production function (`replacement_slots`, scratch copy of the commit): rerun 1 `{owner_floor_state: FAIL, bytes inexact}` gives `scored False`; rerun 2 `{owner_floor_state: PASS, bytes exact}` gives `slots == {original: replacement-2}`. The FAIL appears nowhere in the owner-floor count (`result["parts"]["owner_false_activation"]` counts only the scored slot). The code follows B literally. The rule needs one sentence: any definite failure (a positive owner read before R2, a deterministic-activation failure) in any run of a slot, scored or not, stands and is counted; "not scored" removes only the run's non-failing measurements. An unfixed B lets the mandated rerun rate (about the honest-scan rate) launder a zero-tolerance floor. I judged it "contradictory" rather than "inadequate" because both texts are individually clear and cannot both hold in that case.

## 2. Blocking findings (D4)

### B-1. A declared replacement is scored for a slot that has no open package-access question (outcome selection)

- Where: `qualification/ssdp70/eval/batch_assess70.py:498` `replacement_slots`, the `safe` predicate at `:555`, `observation_adjudicated` at `:611`, and the fallback `needed = [...] or [...]` at `:577`.
- Accepted rule: contract item 13: replacement is for "an observation-inexact original ... for a run UNRESOLVED on the owner floor and for a non-T7 burden run ... INADMISSIBLE only because the observation is not exact"; contract revision-15 effect (b)/(d) justifies it as "within §5 because the original is an observation failure"; §5: "report unresolved rather than selecting the favorable run". Clarification B: "one slot, one scored run".
- Failing trajectory (executed, scratch copy of the commit): original `COMPLETE_ADMISSIBLE`, observation exact, `owner_floor_state` PASS, all dispositions `pass`, plus any manifest-declared replacement run: `replacement_slots` returns `{original: replacement}` with `scored True` for question `owner-floor` (bound present or absent) and for question `bytes` with a bound. A run with only the byte question open, no frozen bound, owner floor PASS, and a replacement declared with question `owner-floor` is also scored (the slot's non-byte criteria are then taken from the rerun). Reason: `observation_adjudicated` accepts `evidence_state == COMPLETE_ADMISSIBLE` as a form of "observation adjudicated", nothing requires the original to appear in `report["required"]` for the declared question, and the `needed` fallback invents a question when none is open.
- Why it matters: the campaign manifest is frozen before launch and bound into every run identity, so replacements are pre-declared reserves; the aggregator is the only place that can refuse a reserve whose original needed no replacement. Today a pre-declared reserve overrides a clean original. The direction is not always harmful (an original with all-pass dispositions cannot be improved on doctrine items), but it changes every non-disposition measure that feeds the 2.0x burden bound, report-length and elapsed-time medians, and it spends the two-rerun cap.
- Minimal fix route (owner: D4, `batch_assess70.replacement_slots`; no D3 change): for each replacement request require that the original has an open question in `report["required"]` that the declared `question` can answer (`bytes` only with a bound, `owner-floor`, `t7-owner-floor` only for a T7 slot with owner floor UNRESOLVED); otherwise raise `ContractError` (fail closed, as for the cap). Add a unit discriminator with an exact, owner-PASS original. Mutation check: the fast suites have no test for this today, so no mutant of the guard can turn red.

### B-2. An unscored replacement's deterministic-activation failure is dropped from the activation count

- Where: `batch_assess70.py:341-380` `score_slots`, lines `373` and `380`: `key_criteria[...]["deterministic activation"]` is recomputed from the **scored slots only**, replacing the earlier computation that covered every declared run.
- Accepted rule: contract §3 and §1 item 12: "every declared deterministic run is delivered ... The count includes all launched runs, inadmissible ones among them"; "rerunning it cannot rescue that failure"; §5 "a replacement never removes the original".
- Failing trajectory (executed, committed code): original exact-for-nothing, observation-inexact, activation PASS; a declared deterministic replacement that was **undelivered** (`criteria["deterministic activation"] == "FAIL"`, `evidence_state INADMISSIBLE`). `safe` is false (the replacement's activation FAIL), so the record is unscored with reason "replacement unavailable, inexact, or original adjudication bars it". The result is `key_criteria[key] == {"deterministic activation": "PASS", "declared_deterministic_runs": 18, "delivered": 18}`: a launched, declared, undelivered deterministic run no longer counts, so a later scored replacement can hide it. The same slot-only recomputation drops the harness/admissibility state of unscored reserves.
- Consequence: the profile's activation criterion can PASS with a launched undelivered deterministic run, which the contract says fails the profile directly.
- Minimal fix route (owner: D4, `score_slots`): compute the activation criterion over all declared deterministic realizations (as the pre-slot code did, `aggregate_assessments` lines ~300-316) and take only measures and doctrine outcomes from scored slots. Add a discriminator in `SlotScoringComposition` with an undelivered unscored replacement. The author's uncommitted working-tree edit (below) appears to address this finding (`declared_failure`); I did not review or test it.

Neither blocker produces a false PASS on the owner floor or on a burden byte total by itself. B-2 can produce a false PASS of the activation criterion. B-1 permits outcome selection.
